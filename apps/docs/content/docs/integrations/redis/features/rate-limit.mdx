title: Rate Limit
description: redisRateLimit reference and behavior
---

`redisRateLimit` is a `RateLimiterAdapter` backed by Redis, so request, token, concurrency, and
AIMD state are shared across every process using the same keys. See [Rate
Limiting](/docs/core/rate-limiting) for the full wait and AIMD behavior this adapter shares with
the built-in in-process limiter.

```ts title="redis-rate-limit-full.ts"
import Redis from 'ioredis';
import { redisRateLimit } from 'vern-llm-redis';
import { fromIoredis } from 'vern-llm-redis/clients';

const client = fromIoredis(new Redis());

const limiter = redisRateLimit(client, {
  requestsPerMinute: 500,
  tokensPerMinute: 200_000,
  maxConcurrent: 20,
});
```

## Options

| Option               | Default                 | Notes                                                                                                                                                    |
| -------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `requestsPerMinute`  | unlimited               | `0` or at least 1. Also the AIMD ceiling's starting value when `aimd` is set, capped at `aimd.maxCapacity`.                                              |
| `tokensPerMinute`    | unlimited               | `0` or at least 1. Checked against a pre-flight estimate from `estimateTokens`.                                                                          |
| `maxConcurrent`      | unlimited               | A whole number. Max requests in flight at once, shared across every process using this key.                                                              |
| `maxQueueMs`         | `30000`                 | Max time a call may wait for capacity before throwing. `0` waits indefinitely, at most `2147483647`.                                                     |
| `maxQueueSize`       | unbounded               | Max calls waiting at once across every process before new ones throw `rate_limit_queue_full`. See [Fair queue](#fair-queue).                             |
| `estimateFraction`   | `1`                     | Scales the pre-flight token estimate down. Above 1 is clamped to 1, must be greater than 0.                                                              |
| `fairQueue`          | `true`                  | Serve waiters first come first served across every process. See [Fair queue](#fair-queue).                                                               |
| `queueLeaseMs`       | `15000`                 | How long a waiter's place in line survives without renewal, so a crashed waiter stops blocking it.                                                       |
| `logger`             | the instance's logger   | Where background failures are reported. Defaults to the `logger` of the `VernLLM` it is passed to, or the one created last if several share the adapter. |
| `concurrencyLeaseMs` | `30000`                 | How long a concurrency slot may go unrenewed before Redis frees it. Live calls renew automatically.                                                      |
| `pollIntervalMs`     | `250`                   | Fallback poll interval used only while waiting on the concurrency bucket without a subscriber.                                                           |
| `estimateTokens`     | `defaultEstimateTokens` | Same tokenizer seam described in [Customization → Tokenizer](/docs/customization/tokenizer).                                                             |
| `keyPrefix`          | `'vernllm:rl'`          | Prefix for every Redis key this adapter writes.                                                                                                          |
| `aimd`               | none                    | AIMD against the requests-per-minute bucket, shared across every process. Requires `requestsPerMinute`.                                                  |
| `subscriber`         | none                    | A dedicated pub or sub connection. Enables push based wake-ups for concurrency waits.                                                                    |

`requestsPerMinute`, `tokensPerMinute`, and `maxConcurrent` are independent limits, set any
combination of them, a call waits on whichever bucket it hits first.

## Precise waits vs polled waits

<Callout type="info">
  Requests/min and tokens/min waits are precise: each computes exactly how long until its bucket
  refills and sleeps that long, capped at 5 seconds so a very low rate never schedules a
  multi-minute timer that can't react to a meanwhile AIMD grow. They never poll. A concurrency wait
  only clears via an external release though, so without `subscriber` it falls back to polling every
  `pollIntervalMs`; with one, it wakes within a few ms of the release that freed a slot.
</Callout>

<Callout type="warn">
  As with the circuit breaker, `subscriber` must be a separate connection from `client`, wrapped
  with `fromIoredisSubscriber` or `fromNodeRedisSubscriber`.
</Callout>

## Concurrency slots survive crashes

Each in flight call holds a lease that it renews while it runs. If a process dies, its leases stop
being renewed and lapse after `concurrencyLeaseMs`, so a crash can no longer shrink `maxConcurrent`
for good. The lease only decides how fast a dead process's slots come back, not how long a call may
run.

All refill timing uses the Redis clock, so a process with a skewed clock cannot refill a bucket early
or stall it for everyone else. Redis 5 or newer is required.

## Fair queue

Waiters are served first come first served across every process sharing the limiter, so capacity goes
to whoever has waited longest rather than whoever's poll fires first. A call that has to wait takes a
ticket in one shared Redis line, only the call at the head may take capacity, and a newcomer that
finds anyone waiting joins behind them instead of taking capacity out from under them. A release
wakes the next waiter through the subscriber, or the poll if there is none.

A waiter renews its place on every check. If its process dies, the place lapses after
`queueLeaseMs` and the line moves on. The order is strict, so a large request at the head is not
starved by small ones behind it, and also holds everyone behind it while it waits for capacity. Set
`fairQueue: false` to skip the line and race, which saves a few Redis calls per waiting call.

The line also counts waiters for `maxQueueSize`, across every process. Without `fairQueue`, a waiting
call joins it only when `maxQueueSize` is set, just to be counted.

## Reading state and shutting down

`getState()` is synchronous, as the adapter contract requires, so it cannot ask Redis. It reports
what this process last saw, refilled forward by the time since, and it applies this process's own
releases and refunds immediately. Other processes' activity is invisible to it, and before this
process has made a call it reports every bucket as untouched. Use `await limiter.readState()`, or `await llm.readRateLimitState()` from `VernLLM`, for a
live read across every process, which also refreshes what `getState()` reports.

`limiter.dispose()` stops the lease renewals and detaches from the subscriber, call it before closing
the client. Several adapters can share one subscriber: a channel stays subscribed until the last
adapter using it is disposed.

## AIMD

```ts title="redis-rate-limit-aimd.ts"
const limiter = redisRateLimit(client, {
  requestsPerMinute: 500,
  aimd: {
    increaseBy: 10,
    decreaseFactor: 0.5,
    minCapacity: 50,
    maxCapacity: 500,
  },
});
```

`aimd` requires `requestsPerMinute` to be set, it's the ceiling AIMD adjusts. `increaseBy` is added
on every recorded successful release; `decreaseFactor` (greater than 0, at most 1) is multiplied
against the ceiling on a rate-limit signal; `minCapacity`/`maxCapacity` bound how far it can shrink
or grow. Set `proactiveFloor` to shrink ahead of a hard limit once a provider hint reports
`remainingRequests` at or below that number.

The ceiling lives in its own Redis key, `{keyPrefix:rpm}:aimd`, so a shrink or growth triggered by one
process is respected by every other process on their next take. That key never expires, so an idle
limiter keeps what it learned. It starts at `requestsPerMinute`, or `maxCapacity` if that is lower,
and shares the bucket's cluster hash slot. Like core, the ceiling shrinks at most once a minute, and
that minute is kept in Redis, so a burst of 429s across every process shrinks it once. See [Rate Limiting → AIMD](/docs/core/rate-limiting#aimd) for how the increase or decrease
curve itself works, that math is identical to the in-process limiter.

## Errors

`acquire` throws `LLMError` in these cases:

| type           | code                           | When                                                                                                              |
| -------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `rate_limited` | `rate_limit_capacity_exceeded` | The estimated tokens exceed a fixed `tokensPerMinute`, which AIMD never grows. Thrown at once instead of waiting. |
| `rate_limited` | `rate_limit_queue_full`        | `maxQueueSize` calls, from any process, were already waiting.                                                     |
| `rate_limited` | `rate_limit_queue_timeout`     | The call waited `maxQueueMs` without capacity becoming available.                                                 |
| `aborted`      | none                           | The `AbortSignal` passed to `acquire` fired while it was waiting.                                                 |
| `network`      | `connection_failed`            | Redis failed. The original error is the `cause`. `readState` throws the same.                                     |

Construction time mistakes throw `LLMError('invalid_params')` from `redisRateLimit(...)` itself,
before any Redis call. The limits follow the same rules, with the same messages, as core's
[Rate Limiting](/docs/core/rate-limiting#options-reference), so a config moves between the two
unchanged.

## Redis unavailable

A Redis failure inside `acquire` fails that attempt with `network` and `connection_failed`. `vern-llm`
retries it like any other network error, and never counts it toward the circuit breaker, since no
provider request was made. There is no fail open path for rate limiting.

Work after a call has succeeded is different: a failed release, token refund, lease renewal or AIMD
resize is logged and swallowed, so an outage cannot crash the process for a call that finished. If
Redis fails between two bucket takes, the buckets already taken are given back first.
