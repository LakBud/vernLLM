`bedrockGuardrail` is a detector: a function from text segments to findings, run through a guardrail
you manage in Amazon Bedrock. It reads topics, content filters, sensitive information, regexes and
word lists, and returns what they found. What to do about a finding is up to the caller.

It comes from its own entry point, `vern-llm-bedrock/guardrail`, so `fromBedrock` and its size are
unchanged. It uses the same `@aws-sdk/client-bedrock-runtime` peer as the adapter.

## Usage

```ts title="bedrock-guardrail.ts"
import { BedrockRuntimeClient } from '@aws-sdk/client-bedrock-runtime';
import { bedrockGuardrail } from 'vern-llm-bedrock/guardrail';

const aws = bedrockGuardrail({
  client: new BedrockRuntimeClient({ region: 'eu-west-1' }),
  guardrailIdentifier: 'gr-abc123',
  guardrailVersion: '3',
});

const signal = AbortSignal.timeout(5000);
const found = await aws([{ text: 'Mail jane@acme.com', source: 'user' }], signal);
// [{ segment: 0, label: 'pii.EMAIL', start: 5, end: 18 }]

const topics = aws.only('topic'); // a detector for some kinds, over the same requests and cache
```

A segment is `{ text, source }`, with `source` one of `user`, `tool`, `system`, `assistant` or
`output`. `output` is read as Bedrock's `OUTPUT`, every other source as `INPUT`. A finding names its
segment by index, and carries offsets when it can locate the text.

<Callout>
  To run it as a check on every call, with labels for policy, redaction and blocking, give it to
  `vern-llm-guard`. See [Hosted
  detectors](/docs/extensions/guard/features/hosted-detectors#bedrockguardrail).
</Callout>

The text you check is sent to Bedrock, and so are images when `images` is on, and the identity behind the client needs
`bedrock:ApplyGuardrail` on the guardrail.

## Findings

| Assessment item                          | Label                     | Span                          |
| ---------------------------------------- | ------------------------- | ----------------------------- |
| `sensitiveInformationPolicy.piiEntities` | `pii.<type>`, `pii.EMAIL` | Every occurrence of the match |
| `sensitiveInformationPolicy.regexes`     | `regex.<name>`            | Every occurrence of the match |
| `wordPolicy.customWords`                 | `word.custom`             | Every whole word occurrence   |
| `wordPolicy.managedWordLists`            | `word.<type>`             | Every occurrence of the match |
| `topicPolicy.topics`                     | `topic.<name>`            | The whole text                |
| `contentPolicy.filters`                  | `content.<type>`          | The whole text                |

- Bedrock returns the matched string for sensitive information and words, so it is located in the
  text. A match that cannot be found gives a finding over the whole text, so a caller that needs
  positions can refuse it rather than miss a value
- An item counts when `detected` is `true`, or when `detected` is absent and its action is not `NONE`.
  A guardrail in detect mode works too
- Bedrock's own action is ignored. Guardrails enforced for the account or organization arrive in the
  same assessments and count the same
- `only(...)` takes `pii`, `regex`, `word`, `topic` and `content`. An unknown kind is an error

## Images

Images are off by default. Set `images: true` and a segment `{ image: { data, mimeType }, source }`
is sent as its own request, with `data` as base64 and no `data:` prefix. In `vern-llm-guard` a check
on user messages gives the detector the images in the request.

- Bedrock takes PNG and JPEG only, up to 4 MB and 8000 by 8000 pixels. The size is read from the
  image header before anything is sent
- Image filters are content filters only, so a finding is `content.<type>` over the whole image,
  with no span. Bedrock reads only the first 100 words of text inside an image
- Which categories apply to images depends on the Region. See AWS's table for [image content
  filters](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-mmfilter.html)
- Bedrock allows 25 images a second, so `imageConcurrency` caps image requests apart from text
- An image is cached by a hash of its data, so one that comes back in the history is sent once
- An image Bedrock cannot take fails the check, so `onError` decides and `closed` blocks the call.
  With `unsupportedImages: 'skip'` it is counted as unscanned instead. Use `skip` when a missed
  image is better than a blocked call, such as a chat that accepts WebP

## Grounding

`aws.grounding(...)` judges an answer against the tool results of the call, with the guardrail's
contextual grounding check. It reads the call around the answer, so it is for output checks.

```ts title="bedrock-grounding.ts"
const grounded = aws.grounding({ sources: ['tool'] });
const found = await grounded([{ text: 'It is Lyon.', source: 'output' }], signal, {
  input: [
    { text: 'Paris is the capital of France.', source: 'tool' },
    { text: 'What is the capital of France?', source: 'user' },
  ],
});
// [{ segment: 0, label: 'grounding.GROUNDING', start: 0, end: 11 }]
```

In `vern-llm-guard` the call is given for you:

```ts title="guard-grounding.ts"
{ id: 'grounded', detect: aws.grounding(), on: 'output', action: 'block' }
```

- **Sources:** each input segment from `sources` (default `['tool']`) is its own grounding source.
  Bedrock takes up to 100000 characters in total, and more fails the check
- **Question:** the last user text, up to 1000 characters. A longer question is sent as its last
  1000 characters (`queryOverflow: 'tail'`, the default) or fails the check (`'error'`). Without a
  user text, only grounding is judged
- **Answer:** sent in chunks of 5000 characters, each against the same sources and question
- **Findings:** `grounding.GROUNDING` for an answer the sources do not support, and
  `grounding.RELEVANCE` for one that does not address the question. A chunk that fails covers its
  own span, so a check can block, label or mask it. The thresholds are the guardrail's, set in AWS
- **No source, no check:** a call without the sources returns no findings and sends nothing
- **Only grounding:** the other policies of the guardrail are not read here, and the sources and
  the question are not checked by them
- **Cache:** keyed by the sources, the question and the answer together, since the verdict depends on
  all three. `DRAFT` disables it, as for the rest of the detector
- Used as an input check, it fails with an error, since the call is not there yet

<Callout type="warn">
  On a stream, Bedrock judges each chunk and calls the whole answer relevant if any chunk is, and
  grounding needs the text to judge. Use `release: 'immediate'` so the final answer is judged and a
  block ends the stream, or a plain call.
</Callout>

## How it runs

- Views and calls share the requests in flight and the cached results, so a text that is already
  being checked, or whose result is cached, is not sent again. A cache miss makes one request per
  chunk of the text, and the same text is sent again when the cache is off, an entry was evicted or
  the version is `DRAFT`. A request that nobody waits for any more is cancelled
- A request carries one chunk of text or one image, since Bedrock returns assessments per guardrail
  and not per content block. A grounding request also carries its sources and question. Bedrock bills per text unit, rounded up for each request
- The cache holds labels and offsets, never text. A published version can be cached, a `DRAFT`
  cannot
- Any error is thrown as it is: throttling, access denied, a response without assessments. The
  caller decides what a failure means
- The SDK's own retries apply. Pass `maxAttempts: 1` to the client if another layer should own them,
  and keep the caller's timeout in mind, since a retried request takes longer
