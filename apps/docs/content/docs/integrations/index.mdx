Core `vern-llm` runs inside one process with zero runtime dependencies. That covers most of what a
call needs, but some things live outside the process: state that several processes have to agree
on, telemetry that belongs in the tools you already run, and providers that come with their own SDK.
Integrations are the optional packages that connect VernLLM to that infrastructure, so core never
has to depend on a store, a vendor, or a cloud.

## What an integration is

An integration is a separate package that implements an extension point core already exposes. Your
calls don't change, only what backs them:

| Extension point                                               | What an integration can back it with         |
| ------------------------------------------------------------- | -------------------------------------------- |
| `CircuitBreakerAdapter`, `RateLimiterAdapter`, `CacheAdapter` | A shared store, so every process acts as one |
| Middleware                                                    | Telemetry, tracing, or policy tooling        |
| `LLMClient`                                                   | A provider SDK that needs its own adapter    |

Because each one sits behind the same interface as the built in version, the guarantees stay the
same. A breaker still ignores caller errors, a cache still fails open, and a fallback target still
never inherits the primary's breaker or limiter.

## When to add one

Start without any. Reach for an integration when one of these becomes true:

- **Your app runs as more than one process.** In memory, each process only knows its own half of the
  story: rate limits multiply by the number of processes, and a breaker that opened in one keeps
  sending traffic from the rest.
- **You want calls in your observability stack.** Events are already reported in process. An
  integration turns them into the traces and metrics your backend understands.
- **Your provider needs its own SDK.** OpenAI compatible providers, Anthropic, and Gemini are built
  in. Others arrive as their own adapter package.

## Why they are separate

<Cards>
  <Card title="Same guarantees">
    Whatever VernLLM protects against in one process keeps working the same way across many.
  </Card>
  <Card title="Nothing forced">
    Core never picks a store, protocol, or vendor for you, and stays at zero runtime dependencies.
  </Card>
  <Card title="Pay for what you use">
    Infrastructure is something you add when you need it, not a cost every install pays.
  </Card>
  <Card title="Own release schedule">
    Each integration versions on its own. Adding or upgrading one never touches `vern-llm`.
  </Card>
</Cards>

Every integration takes `vern-llm` as a peer dependency, so it shares the copy your app already
uses and an `LLMError` it throws passes your own `instanceof` checks.

## Building your own

Nothing about the official integrations is special. Any package, or code in your own app, can
implement the same interfaces: see [Customization](/docs/customization) for the
[circuit breaker](/docs/customization/circuit-breaker),
[rate limiter](/docs/customization/rate-limiting), [cache](/docs/customization/caching),
[middleware](/docs/customization/middleware), and [provider](/docs/customization/provider)
contracts.

## Community

Each integration has its own Contributing guide and Changelog, since its scripts, test setup, and
release schedule are its own. See [Redis → Contributing](/docs/integrations/redis/contributing) for
an example. The project wide [Code of Conduct](/docs/code-of-conduct) and
[Security](/docs/security) policy cover every integration, the same as `vern-llm` itself.
