---
title: Normalized Caching
description: Matching keys that differ only in case, whitespace, or punctuation
---

A lot of "these should be the same cache entry" cases aren't semantic at all, they're just
formatting differences. `"What is 2+2?"`, `"what is 2+2"`, and `"  WHAT IS 2+2?  "` mean the same
thing and differ only in case, punctuation, and whitespace. `NormalizedCacheAdapter` handles this
class of duplicate for free, with no embedding calls and no external dependencies.

## Usage

```ts title="normalized-cache.ts"
import { NormalizedCacheAdapter, VernLLM } from 'vern-llm';

const llm = new VernLLM({
  client: openai,
  model: 'gpt-4o',
  cache: new NormalizedCacheAdapter(), // wraps InMemoryCacheAdapter by default
});

await llm.cachedCall({
  cacheKey: userQuestion, // pass the raw text, same as with semantic caching
  ttl: 3600,
  call: { systemPrompt: 'Answer concisely.', userContent: userQuestion },
});
```

Like `SemanticCacheAdapter` (see [Semantic Caching](/docs/guides/caching/semantic)), `cacheKey`
here should be the actual prompt text, not a hand-picked id, normalization needs real content to
operate on.

## What it normalizes

The default normalization is intentionally simple:

```ts
key
  .toLowerCase()
  .trim()
  .replace(/[^\p{L}\p{N}\s]/gu, ' ')
  .replace(/\s+/g, ' ')
  .trim();
```

Lowercases, trims leading/trailing whitespace, replaces punctuation with a space, and collapses
repeated whitespace into single spaces (with a final trim to clean up any edge space left behind
by that replacement). This catches formatting noise but nothing more; `"2+2"` and `"2 + 2"` both
normalize to `"2 2"`, since punctuation is replaced with a space rather than deleted outright, so
stripping `+` never collapses adjacent characters together the way outright deletion would.
Normalization is a text transform, not a parser; it doesn't understand what the text means, so
`"2+2"` and `"four"` still normalize differently even though they mean the same thing.

<Callout type="warn">
  If your inputs vary in more than surface formatting, different word choice, different phrasing,
  different language, normalization won't catch it. That's the line between this and semantic
  caching: normalization handles "same words, different formatting"; semantic caching handles
  "different words, same meaning."
</Callout>

## Collision risk

The tradeoff runs the other way too. Collapsing every kind of punctuation into the same single
space closes the false-negative case above, but it can't tell "punctuation used as decoration"
apart from "punctuation used to distinguish two different things": `"order A-1"` and
`"order A:1"` both normalize to `"order a 1"`. If those are genuinely two different orders, a
lookup for one silently returns the cached answer meant for the other, a wrong answer served with
confidence, not a cache miss you'd notice.

This mainly shows up when a prompt embeds a punctuation-delimited identifier, an order or ticket
reference, a phone number, anything where the specific separator character actually distinguishes
one value from another rather than just formatting it. Genuinely-equivalent formatting noise, like
`"2024-01-01"` vs `"2024/01/01"` both meaning the same calendar date, is exactly what this adapter
is supposed to collapse; there's no way for a generic text transform to tell that case apart from
the order-reference case above, since both are "different punctuation, otherwise identical text."

### Fixing it with `preserveChars`

If it's a small, fixed set of separator characters causing the collision, `preserveChars` keeps
them literal instead of stripping them, without writing a full custom adapter:

```ts title="preserve-chars.ts"
const cache = new NormalizedCacheAdapter(undefined, { preserveChars: ':-' });

await cache.set('order A-1', 'Shipped'); // normalizes to "order a-1"
await cache.set('order A:1', 'Delayed'); // normalizes to "order a:1", no longer the same key
```

Everything else still normalizes as before, case, whitespace, and every other punctuation
character are collapsed exactly the way they were without `preserveChars`; only the characters
you list are exempted.

This is a per-adapter, all-or-nothing choice, not a per-key one: a preserved character stops
collapsing everywhere, including cases where it really was decorative. Preserving `+` to protect
an identifier would also un-collapse `"2+2"` from `"2 + 2"`, undoing the example earlier on this
page. Pick characters that are consistently meaningful in your prompts, not ones that are
sometimes decoration and sometimes a real separator, if a character plays both roles depending on
context, `preserveChars` can't help either, and you're back to a custom `resolveKey`.

<Callout type="warn">
  If your prompts embed identifiers where the separator character is meaningful, not decorative, try
  `preserveChars` first. If a single character plays both roles depending on context, or you need
  something more domain-specific (stemming, filler-word stripping, digit-vs-word numbers), write a
  custom `resolveKey` (see [Custom normalization](#custom-normalization) below) instead.
</Callout>

## Wrapping a different inner adapter

`NormalizedCacheAdapter` doesn't do its own storage, it normalizes the key, then delegates to
whatever adapter you pass it. Swap in Redis, Upstash, or any other `CacheAdapter` without changing
the normalization logic:

```ts
const cache = new NormalizedCacheAdapter(new UpstashCacheAdapter());
```

## Custom normalization

The shipped normalization is deliberately generic. If your domain needs something different,
stemming, stripping filler words, normalizing numbers written as words vs digits, write your own
adapter with a custom `resolveKey` rather than trying to configure `NormalizedCacheAdapter`
further:

```ts title="custom-normalized-adapter.ts"
import type { CacheAdapter } from 'vern-llm';

class DomainNormalizedAdapter<T> implements CacheAdapter<T> {
  constructor(private inner: CacheAdapter<T>) {}

  private normalize(key: string): string {
    return (
      key
        .toLowerCase()
        .replace(/\b(please|could you|can you)\b/g, '') // strip filler phrases
        .replace(/[^\w\s]/g, ' ') // replace punctuation with a space, not delete, so adjacent
        // characters/digits don't get glued together (e.g. "2+2" vs "2 + 2")
        .trim()
        .replace(/\s+/g, ' ')
    );
  }

  async resolveKey(key: string) {
    return this.normalize(key);
  }

  get(key: string) {
    return this.inner.get(this.normalize(key));
  }

  set(key: string, value: T, ttl: number) {
    return this.inner.set(this.normalize(key), value, ttl);
  }

  async delete(key: string): Promise<void> {
    await this.inner.delete?.(this.normalize(key));
  }
}
```

This is the same shape as `NormalizedCacheAdapter` itself, the built-in version is just one
reasonable default, not the only option.
