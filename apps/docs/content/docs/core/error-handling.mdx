description: LLMError types, what triggers each, and what gets retried

When a raw API error or unknown thrown error is normalized, the original error is preserved
on `err.cause`, in case the normalized `type`/`status`/`issues` aren't enough to diagnose the
failure. Existing `LLMError` instances are returned unchanged, so internally-created errors such
as timeout, parse, and validation errors may not have a `cause`:

```ts title="error-handling-example.ts"
import { isLLMError } from 'vern-llm';

try {
  const result = await llm.call({ systemPrompt, userContent, schema });
} catch (err) {
  if (isLLMError(err)) {
    switch (err.type) {
      case 'validation':
        console.log(err.issues); // the schema's error object
        break;
      case 'api':
        console.log(err.status); // HTTP status, if the provider returned one
        console.log(err.cause); // the original error thrown by the provider client
        console.log(err.retryAfterMs); // Retry-After from the last attempt, if the provider sent one
        break;
      case 'circuit_open':
        // provider is down, back off and do not retry immediately
        break;
    }
  }
  throw err;
}
```

## Error types

<Cards>
  <Card title="timeout">
    A single attempt exceeded `timeoutMs`. Retried like any other transient failure.
  </Card>
  <Card title="api">
    The provider returned an HTTP error with a status code. Retried unless the status is in
    `nonRetryableStatus` (default `400, 401, 403, 404, 422`).
  </Card>
  <Card title="parse">
    The response content was not valid JSON. Never retried because a malformed response will not fix
    itself on retry.
  </Card>
  <Card title="validation">
    JSON parsed successfully but failed `schema.safeParse`. Never retried for the same reason as
    `parse`. Carries `.issues` with the validator's error object. Note that usage tracking may have
    already reported the provider response before this validation failure occurs.
  </Card>
  <Card title="quota_exceeded">
    The usage reservation failed before the request was sent. This happens when `reserveUsage`
    rejects and the original error is preserved on `err.cause`.
  </Card>
  <Card title="circuit_open">
    The circuit breaker is open because the provider has failed too many times in a row. Fails
    immediately without hitting the provider.
  </Card>
  <Card title="aborted">
    The caller's `AbortSignal` fired. This represents intentional cancellation by the caller, not a
    timeout. See <a href="/docs/core/cancellation">Cancellation</a>.
  </Card>
  <Card title="unknown">
    Anything that does not fit the above categories, including network errors with no status code
    and unexpected provider responses. Retried by default.
  </Card>
</Cards>

## What gets retried

`shouldRetry` skips a retry when any of these are true:

- The signal has already aborted
- `error.type` is `'parse'` or `'validation'` because these are deterministic response-processing failures rather than transient provider faults, so retrying will not help
- `error.status` is in `nonRetryableStatus` (default `[400, 401, 403, 404, 422]`)

Everything else, including timeouts, 5xx errors, network failures, and unknown errors, is retried up to
`maxRetries`. If the failed attempt's error carries a `Retry-After` header (delta-seconds or
HTTP-date form), that value is honored for the wait, capped at the same max delay as backoff.
Otherwise the wait falls back to exponential backoff with jitter.

<Callout type="warn">
  Exhausting all retries also records a circuit breaker failure if one is configured and throws the
  final normalized `LLMError`. For raw API or unknown thrown errors, the underlying error is
  preserved on `err.cause`, so it's still available even though the top-level `message` is a generic
  `'LLM request failed'`. Existing `LLMError` instances are not wrapped again, so some error types
  (such as timeout, parse, and validation) may not have a `cause`.
</Callout>

## Debugging a failed call

When `debug: true` is set, a failure is also logged through the injected logger's `debug` method,
independent of catching the thrown `LLMError` yourself:

```ts title="debug-logging-setup.ts"
const llm = new VernLLM({ client, model, debug: true });
```

```console title="debug-log-output"
[vern:<requestId>] error:
<the provider's error message or response body>
```

This is useful when a failure happens somewhere you aren't directly awaiting the `call()` (for
example, inside `cachedCall`'s coalesced callers), since the log fires regardless of which caller
ends up seeing the thrown error.
