description: Wrap calls with cachedCall or cachedLLMCall

```ts title="cached-call-setup.ts"
import { InMemoryCacheAdapter } from 'vern-llm';

const llm = new VernLLM({
  client: openai,
  model: 'gpt-4o',
  cache: new InMemoryCacheAdapter(), // swap for your own Redis/Upstash adapter
});

const result = await llm.cachedCall({
  cacheKey: `cv:${cvId}`,
  ttl: 3600,
  fn: () => llm.call({ systemPrompt, userContent }),
  reserveUsage: ({ coalesced }) => quota.reserve(userId, { coalesced }),
  refundUsage: ({ coalesced }) => quota.refund(userId, { coalesced }),
});
```

<Callout type="warn">
  `ttl` is in seconds, not milliseconds. `ttl: 3600` caches for one hour. This differs from most
  other timing options in the library (`timeoutMs`, `baseDelayMs`), which are milliseconds, so it's
  worth double-checking if you're copying a value across.
</Callout>

<Callout>
  `refundUsage` only runs if `reserveUsage` actually succeeded for that caller. If `refundUsage`
  itself throws, that failure is logged and swallowed. The original error from `fn` (or the cache
  write) is what propagates, so a broken refund path never masks the real failure.
</Callout>

## Concurrent misses are coalesced

If several calls with the same `cacheKey` miss the cache at roughly the same time, only the first one (the "trigger") actually calls `fn`. Every other concurrent caller waits on that same in-flight call instead of starting its own, and all of them resolve (or reject) together once it settles. This prevents a cache stampede, where many simultaneous callers all trigger their own (possibly expensive) `fn()` call before the first one has had a chance to populate the cache.

Every caller still gets its own `reserveUsage`/`refundUsage` invocation — the trigger and each coalesced caller — but is told whether it was coalesced via the `coalesced` flag, so your application decides how coalesced callers are billed: full price, a reduced rate, or not billed at all.

<Callout>
  Although `fn` executes only once per in-flight window, `reserveUsage` and `refundUsage` are still
  invoked once per caller. If `fn` fails, every caller is refunded independently.
</Callout>

## How the cache/reserve/refund flow works

On a cache miss, `cachedCall` runs in this order for the triggering caller:

1. `reserveUsage({ coalesced: false })`, if provided.
2. `fn()`, the actual LLM call.
3. On success, write the result to the cache (a failed cache write is logged and swallowed; the result is still returned).
4. On any failure in steps 1 or 2, call `refundUsage({ coalesced: false })`, then rethrow the original error.

Coalesced callers skip step 2 (they share the trigger's `fn()` call instead) but still run their own `reserveUsage({ coalesced: true })` before waiting on the shared result, and their own `refundUsage({ coalesced: true })` if it fails.

<Callout type="warn">
  `refundUsage` only runs for a given caller if that caller's own `reserveUsage` succeeded first. If
  `reserveUsage` itself throws (e.g. the user is already out of quota), that error propagates
  directly and `refundUsage` is **not** invoked — there was nothing reserved to give back. You don't
  need to guard your `refundUsage` implementation against being called for a reservation that was
  never made.
</Callout>

<Callout type="warn">
  Cache adapters use the `hit` field to indicate whether a value exists, not the presence of
  `value` alone. This lets a legitimately cached `null` be served from cache instead of being
  treated as a miss. `{ hit: true, value: null }` means "we have a cached result, and it's
  `null`." `{ hit: false, value: null }` means "nothing is cached for this key."
</Callout>

## Deleting cached entries

Cache invalidation is application-specific, so VernLLM does not automatically
decide when a cached response becomes stale. When your application knows that a
cached response should no longer be used, you can remove the entry manually:

```ts
await llm.deleteCache(`cv:${cvId}`);
```

## `cachedLLMCall`: cached + retried in one call

`cachedCall` is a thin cache wrapper; it doesn't apply retry/timeout/circuit-breaker behavior on its own. If `fn` is always going to be `() => llm.call(...)`, `cachedLLMCall` wires that up for you:

```ts title="cached-llm-call.ts"
const result = await llm.cachedLLMCall({
  cacheKey: `cv:${cvId}`,
  ttl: 3600,
  call: { systemPrompt, userContent }, // same shape as call()'s params
  reserveUsage: ({ coalesced }) => quota.reserve(userId, { coalesced }),
  refundUsage: ({ coalesced }) => quota.refund(userId, { coalesced }),
});
```

## Choosing a cache key

There's no automatic key derivation from the call's contents. `cacheKey` is entirely up to you, which means it's also easy to get wrong: if you reuse a key across calls with a different `systemPrompt`, `schema`, or `model`, you'll get a cached result that doesn't match what the new call would have produced.

A safer pattern is to fold the things that affect the output into the key itself:

```ts
const cacheKey = `cv:${cvId}:${model}:v2`; // bump the version suffix when the prompt/schema changes
```

## Custom cache adapter

```ts title="upstash-cache-adapter.ts"
import type { CacheAdapter } from 'vern-llm';

class UpstashCacheAdapter implements CacheAdapter {
  async get(key: string) {
    const raw = await redis.get(key);

    if (raw === null) {
      return { hit: false, value: null };
    }

    return { hit: true, value: JSON.parse(raw) };
  }

  async set(key: string, value: unknown, ttl: number) {
    await redis.set(key, JSON.stringify(value), { ex: ttl });
  }

  async delete(key: string) {
    await redis.del(key);
  }
}
```

<Callout>
  The key thing to get right when migrating: `hit` should be `true` whenever the key existed in your
  underlying store, even if the stored value itself is `null`. `hit` should only be `false` when
  nothing was found for that key. Most stores already give you this signal for free — e.g. Redis's
  `GET` returning `null` for "key doesn't exist" is different from a `null` you stored yourself, so
  make sure your adapter checks existence rather than just checking `value !== null`.
</Callout>

<Callout>
  The built-in `InMemoryCacheAdapter` treats `ttl` as seconds, supports deletion, and accepts an
  optional `maxSize` limit to prevent unbounded memory growth. When the limit is reached, the oldest
  entries are removed first. Custom adapters should keep the same `ttl` convention (rather than
  milliseconds) so behavior stays consistent across adapters. Implement `delete` if your storage
  backend supports explicit cache invalidation.
</Callout>
