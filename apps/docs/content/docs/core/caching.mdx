description: Wrap calls with cachedCall or cachedLLMCall

The built-in `InMemoryCacheAdapter` provides a simple in-memory cache with no external dependencies.
It is useful for local development or single-process deployments; use a shared adapter such as Redis
or Upstash when multiple processes need the same cache.

```ts title="cached-call-setup.ts"
import { InMemoryCacheAdapter } from 'vern-llm';

const llm = new VernLLM({
  client: openai,
  model: 'gpt-4o',
  cache: new InMemoryCacheAdapter(1000), // maxSize limit; defaults to 1000
});

const result = await llm.cachedCall({
  cacheKey: `cv:${cvId}`,
  ttl: 3600,
  fn: () => llm.call({ systemPrompt, userContent }),
});
```

<Callout type="warn">
  `ttl` is in seconds, not milliseconds. `ttl: 3600` caches for one hour. This differs from most
  other timing options in the library (`timeoutMs`, `baseDelayMs`), which are milliseconds, so it's
  worth double-checking if you're copying a value across.
</Callout>

## Concurrent misses are coalesced

If several calls with the same `cacheKey` miss the cache at roughly the same time, only the first one
(the "trigger") actually calls `fn`. Every other concurrent caller waits on that same in-flight call
instead of starting its own, and all of them resolve (or reject) together once it settles.

This prevents a cache stampede where many simultaneous callers trigger their own expensive `fn()`
operation before the first one has populated the cache.

Each coalesced caller has its own `signal` and its own usage-hook lifecycle. Aborting one coalesced
caller does not cancel the shared in-flight `fn` operation for other callers.

<Callout>
Although `fn` executes only once per in-flight window, usage metering still runs per caller. Each
caller performs its own `reserveUsage` and, if that reservation succeeds, gets its own
`refundUsage` lifecycle.

A coalesced caller can fail with `LLMError('quota_exceeded')` if its own reservation is rejected,
while the original trigger caller continues with the shared `fn` operation. Successful callers
still receive the same resolved value or error from the shared operation.

</Callout>

<Callout type="warn">
  Cache adapters use the `hit` field to indicate whether a value exists, not the presence of
  `value` alone. This lets a legitimately cached `null` be served from cache instead of being
  treated as a miss. `{ hit: true, value: null }` means "we have a cached result, and it's
  `null`." `{ hit: false, value: null }` means "nothing is cached for this key."
</Callout>

## Deleting cached entries

Cache invalidation is application-specific, so VernLLM does not automatically decide when a cached
response becomes stale. When your application knows that a cached response should no longer be used,
you can remove the entry manually:

```ts
await llm.deleteCache(`cv:${cvId}`);
```

## `cachedCall`: cache wrapper

`cachedCall` manages cache lookup, cache writes, concurrent miss coalescing, and optional usage
metering. It does not apply retry, timeout, or circuit-breaker behavior by itself.

When `reserveUsage` and `refundUsage` are provided, they run once per caller on cache misses,
including coalesced callers. The `coalesced` value passed to the hooks indicates whether the
caller joined an existing in-flight operation.

`signal` can be provided to cancel that caller's cached operation. The caller's signal is passed to
`reserveUsage` and `refundUsage` as part of the hook context. For `cachedCall`, a top-level
`signal` does not automatically cancel the operation inside `fn`; pass it to the wrapped operation
as well if it should be cancelled. Aborting one coalesced caller does not cancel the shared
in-flight operation used by other callers.

Put whatever operation you want cached inside `fn`. If that operation is a VernLLM request, call
`llm.call()` inside it so the normal retry, timeout, and circuit-breaker pipeline still applies:

```ts title="cached-call-custom.ts"
const result = await llm.cachedCall({
  cacheKey: `cv:${cvId}`,
  ttl: 3600,
  signal,
  fn: async () => {
    return llm.call({
      systemPrompt,
      userContent,
      signal,
    });
  },
});
```

## `cachedLLMCall`: cached + retried in one call

`cachedLLMCall` is a convenience wrapper for the common case where the cached operation is a
`llm.call()` invocation.

Usage hooks are applied at the cache level. Do not also provide `reserveUsage` or `refundUsage`
inside the nested `call` options; those are ignored to avoid reserving twice for the same logical
request.

`signal` can be provided at the top level to cancel that caller's cached operation lifecycle. Each
coalesced caller has its own signal and usage-hook lifecycle. Aborting one coalesced caller does not
cancel the shared in-flight operation for other callers.

The top-level `signal` only controls the cached wrapper lifecycle. If `fn` starts a request that
should be cancellable, pass the same signal into that operation explicitly.

It combines cache lookup, cache writes, concurrent miss coalescing, and the normal
retry/timeout/circuit-breaker behavior from `call()`:

```ts title="cached-llm-call.ts"
const result = await llm.cachedLLMCall({
  cacheKey: `cv:${cvId}`,
  ttl: 3600,
  signal,
  call: {
    systemPrompt,
    userContent,
    signal,
  },
});
```

## Choosing a cache key

There's no automatic key derivation from the call's contents. `cacheKey` is entirely up to you.

If you reuse a key across calls with different `systemPrompt`, `schema`, or `model`, you may receive
a cached result that does not match what the new request would have produced.

A safer pattern is to include values that affect the output:

```ts
const cacheKey = `cv:${cvId}:${model}:v2`; // bump version when prompt/schema changes
```

## Custom cache adapter

```ts title="upstash-cache-adapter.ts"
import type { CacheAdapter } from 'vern-llm';

class UpstashCacheAdapter implements CacheAdapter {
  async get(key: string) {
    const raw = await redis.get(key);

    if (raw === null) {
      return { hit: false, value: null };
    }

    return { hit: true, value: JSON.parse(raw) };
  }

  async set(key: string, value: unknown, ttl: number) {
    await redis.set(key, JSON.stringify(value), { ex: ttl });
  }

  async delete(key: string) {
    await redis.del(key);
  }
}
```

<Callout>
  The key thing to get right when migrating: `hit` should be `true` whenever the key existed in your
  underlying store, even if the stored value itself is `null`. `hit` should only be `false` when
  nothing was found for that key.
</Callout>

<Callout>
  The built-in `InMemoryCacheAdapter` treats `ttl` as seconds, supports deletion, and accepts an
  optional `maxSize` limit to prevent unbounded memory growth. When the limit is reached, the oldest
  entries are removed first.

Custom adapters should keep the same `ttl` convention (seconds, not milliseconds) so behavior
stays consistent across adapters.

</Callout>
