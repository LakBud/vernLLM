## Overview

VernLLM provides an optional response cache for storing completed LLM results and reusing them on
future requests.

Caching is controlled through a `CacheAdapter`. The package includes an in-memory implementation
that works without additional dependencies, while production applications can provide their own
adapter backed by systems such as Redis or Upstash.

```ts title="cache-setup.ts"
import { InMemoryCacheAdapter, VernLLM } from 'vern-llm';

const llm = new VernLLM({
  client: openai,
  model: 'gpt-4o',
  cache: new InMemoryCacheAdapter(),
});
```

<Callout type="info">
  `InMemoryCacheAdapter` stores values only inside the current process. When running multiple
  instances, use a shared cache adapter so all instances can access the same entries.
</Callout>

## cachedCall

`cachedCall` adds caching around any async function.

It checks the cache first and only executes `fn` when no cached value exists.

```ts title="cached-call.ts"
const result = await llm.cachedCall({
  cacheKey: `cv:${cvId}`,
  ttl: 3600,
  fn: () =>
    llm.call({
      systemPrompt,
      userContent,
    }),
});
```

The cache flow is:

1. Look up the provided `cacheKey`.
2. Return the cached value if an entry exists.
3. Execute `fn()` on a cache miss.
4. Store the returned value.
5. Return the result.

<Callout type="warn">
  `ttl` values are seconds, not milliseconds. `ttl: 3600` caches an entry for one hour.
</Callout>

## cachedLLMCall

`cachedLLMCall` combines `cachedCall` with VernLLM's normal `call` pipeline.

Use it when the cached operation is always an LLM request.

```ts title="cached-llm-call.ts"
const result = await llm.cachedLLMCall({
  cacheKey: `cv:${cvId}:v2`,
  ttl: 3600,
  call: {
    systemPrompt,
    userContent,
  },
});
```

This is equivalent to:

```ts title="cached-llm-call-expanded.ts"
const result = await llm.cachedCall({
  cacheKey: `cv:${cvId}:v2`,
  ttl: 3600,
  fn: () =>
    llm.call({
      systemPrompt,
      userContent,
    }),
});
```

Because it uses `call`, cached LLM requests still support:

- retries
- timeouts
- circuit breakers
- JSON parsing
- schema validation
- usage callbacks

## Concurrent cache misses

VernLLM coalesces concurrent cache misses for the same key.

If multiple requests arrive with the same `cacheKey` while the value is missing:

```text
Request A → cache miss → executes fn()
Request B → cache miss → waits for Request A
Request C → cache miss → waits for Request A

              ↓

        one shared result

              ↓

      A, B, and C receive it
```

Only one execution of `fn()` happens during the in-flight window.

<Callout type="info">
  Coalescing prevents duplicate work during simultaneous requests. Once the request completes,
  future requests use the stored cache entry normally.
</Callout>

## Cache keys

VernLLM does not automatically generate cache keys.

The cache key must represent everything that can change the generated result, including:

- prompt contents
- model
- schema
- response format
- application version

For example:

```ts title="cache-key-versioning.ts"
const cacheKey = `cv:${cvId}:${model}:v2`;
```

Increase the version when changing prompts or output requirements.

<Callout type="warn">
  Reusing the same cache key for different requests can return an older response that does not match
  the new request.
</Callout>

## Deleting cached entries

Cache invalidation is controlled by the application.

When a cached value should no longer be used, remove it manually.

```ts title="delete-cache.ts"
await llm.deleteCache(`cv:${cvId}`);
```

The cache adapter determines whether deletion is supported.

<Callout type="info">
  `delete` is optional on `CacheAdapter`. If the configured adapter does not support deletion,
  `deleteCache` safely does nothing.
</Callout>

## CacheAdapter

Custom cache implementations must implement the `CacheAdapter` interface.

```ts title="cache-adapter.ts"
export interface CacheAdapter<T = unknown> {
  get(key: string): Promise<{
    hit: boolean;
    value: T | null;
  }>;

  set(key: string, value: T, ttl: number): Promise<void>;

  delete?(key: string): Promise<void>;
}
```

## Cache hits and null values

Cache adapters use the `hit` field to indicate whether an entry exists.

The presence of `value` alone is not enough because `null` is a valid cached value.

```ts title="cache-results.ts"
{
  hit: true,
  value: null,
}
```

This means:

> A cached entry exists and its stored value is `null`.

A cache miss looks like:

```ts title="cache-miss.ts"
{
  hit: false,
  value: null,
}
```

This means:

> No entry exists for this key.

<Callout type="warn">
  Do not implement cache adapters by checking only whether `value !== null`. A stored `null` value
  must still be treated as a cache hit.
</Callout>

## Built-in InMemoryCacheAdapter

The built-in adapter:

- requires no external dependencies
- stores values inside memory
- supports TTL expiration
- supports deletion
- limits memory usage with `maxSize`

```ts title="memory-cache-options.ts"
const cache = new InMemoryCacheAdapter({
  maxSize: 1000,
});
```

When the size limit is reached, the oldest entries are removed first.

<Callout>
  All cache adapters should follow the same TTL convention: seconds, not milliseconds.
</Callout>
