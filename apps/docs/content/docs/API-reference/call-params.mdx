---
title: Call Params
description: Every field accepted by call(), cachedCall(), and their defaults
---

`call()` takes a single `CallParams<T>` object. `userContent` is the only required field; everything
else has a default or is simply optional.

```ts title="call-params-basic-usage.ts"
const result = await llm.call({
  systemPrompt: 'You are a helpful assistant.',
  userContent: 'Summarize this text.',
  temperature: 0.7,
  maxTokens: 500,
});
```

<Callout>
  `cachedCall`'s `call` field accepts this exact same shape, with one exception: `reserveUsage` and
  `refundUsage` are not supported inside the nested `call` object. If provided there, they are
  ignored and a warning is logged. Pass `reserveUsage`/`refundUsage` at the `cachedCall` top level
  instead. `cachedCall` also accepts a top-level `signal` for the caller's cancellation lifecycle,
  separate from any `signal` set inside `call`.
</Callout>

## Content

### `userContent`

**Required.** `string | ContentBlock[]`. The current user message. Always sent as the final
user turn, after `history` if provided.

A plain `string` is used for text-only prompts (the common case). For multimodal input, pass an
array of text and image blocks:

```ts title="multimodal-user-content.ts"
const result = await llm.call({
  userContent: [
    {
      type: 'text',
      text: 'Describe this image.',
    },
    {
      type: 'image',
      mimeType: 'image/png',
      data: imageBase64,
    },
  ],
});
```

Image blocks use base64-encoded image bytes without a `data:` URL prefix. VernLLM translates
them into each provider's native multimodal format automatically.

Supported image MIME types:

- `image/png`
- `image/jpeg`
- `image/gif`
- `image/webp`

Existing string-based calls remain fully compatible.

<Cards>
  <Card title="systemPrompt">
    `string`, optional. Sent as the system message. Omit it and the provider's own default system
    behavior applies.
  </Card>
  <Card title="history">
    `ConversationTurn[]`, optional. Prior turns, oldest first, not including `userContent`. Turns
    must alternate role, following `user → assistant → user → assistant`, or, once tool calls are
    involved, `user → assistant(toolCalls) → tool → assistant`. A `tool` turn must immediately
    follow an `assistant` turn that set `toolCalls`. History must end on either an `assistant` turn
    without pending tool calls, or a completed `tool` turn, or `call()` throws
    `LLMError('validation')` before any request is made. See{' '}
    <a href="/docs/guides/multi-turn-conversations">Multi-turn Conversations</a>.
  </Card>
</Cards>

## Tool calling

<Cards>
  <Card title="tools">
    `ToolDefinition[]`, optional. Tools the model may call. Setting `tools` changes what `call()`
    returns, from `T` directly to a `CallWithToolsResult<T>` discriminated union. By default,
    mutually exclusive with `jsonSchema` on Anthropic and Bedrock only, except on models opted
    into `nativeStructuredOutputModels`; Gemini and OpenAI-compatible clients never restrict the
    combination at all. Never mutually exclusive with `schema`, on any provider. Must not be an
    empty array. See <a href="/docs/core/tool-calling">Tool Calling</a>.
  </Card>
  <Card title="toolChoice">
    `'auto' | 'none' | 'required' | { name: string }`, optional. Defaults to `'auto'` when `tools`
    is set. Throws `LLMError('validation')` if set without `tools`, or if `{ name }` names a tool
    that is not present in `tools`.
  </Card>
</Cards>

When tool calling is enabled, VernLLM validates the tool calls returned by the model before
returning them to the application.

An `unknown_tool` error is raised when the model requests a tool that was not included in `tools`.
A `duplicate_tool_call_id` error is raised when multiple tool calls in the same response use the
same call ID.

Both errors are represented as `LLMError('api')` with a machine readable `code`:

```ts title="tool-contract-error-codes.ts"
try {
  await llm.call({
    userContent: 'Use the available tools.',
    tools: [weatherTool],
  });
} catch (error) {
  if (isLLMError(error)) {
    if (error.code === 'unknown_tool') {
      console.log('The model requested a tool that was not offered.');
    }

    if (error.code === 'duplicate_tool_call_id') {
      console.log('The model returned the same tool call ID more than once.');
    }
  }
}
```

A single response can contain multiple tool contract problems. When that happens,
`LLMError.toolIssues` contains the complete set of detected issues so the application can handle
them together.

```ts title="tool-contract-issues.ts"
try {
  await llm.call({
    userContent: 'Use the available tools.',
    tools: [weatherTool],
  });
} catch (error) {
  if (isLLMError(error) && error.toolIssues) {
    for (const issue of error.toolIssues) {
      console.log(issue.code, issue.name, issue.toolCallId);
    }
  }
}
```

Tool contract errors are not retried because retrying the same request cannot make an unavailable
tool available or repair a duplicate tool call ID. They also do not count toward the circuit
breaker because they indicate a model response problem rather than a provider availability
failure.

See <a href="/docs/core/tool-calling">Tool Calling</a> for the complete tool contract behavior and

<a href="/docs/core/error-handling">Error Handling</a> for error codes and retry behavior.

## Streaming

<Cards>
  <Card title="stream">
    `boolean`, optional, default `false`. When `true`, `call()` returns a `StreamCallResult<T>`
    (`{ chunks, finalResult }`) instead of resolving directly to `T`. Requires TypeScript to see
    `stream: true` as a literal at the call site to select the streaming overload, see{' '}
    <a href="/docs/core/streaming#a-note-on-the-call-overload">the streaming overload note</a>.
    Combines freely with `tools`, and with `schema`. `jsonSchema` remains mutually exclusive with
    `tools` by default (opt-in exception on Anthropic/Bedrock, see{' '}
    <a href="/docs/core/structured-output#combining-with-tools">Structured Output</a>). See{' '}
    <a href="/docs/core/streaming">Streaming</a>.
  </Card>
  <Card title="chunkIdleTimeoutMs">
    `number`, optional. Only applies when `stream: true`. Overrides the instance's
    `chunkIdleTimeoutMs` for this call, pass `0` or `Infinity` to disable the idle timeout for just
    this call. Useful for routes that need a longer allowance than the instance default, reasoning
    models with long silent gaps, for example. See{' '}
    <a href="/docs/core/streaming#per-chunk-idle-timeout">Per-chunk idle timeout</a>.
  </Card>
</Cards>

## Model & generation

| Field             | Type                                       | Default                                       | Notes                                                                                                                                                                                                                                  |
| ----------------- | ------------------------------------------ | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model`           | `string`                                   | The instance's `model` option                 | Overrides the model for this call only. See <a href="/docs/guides/per-call-overrides">Per-call overrides</a>.                                                                                                                          |
| `temperature`     | `number \| null`                           | `0.2`, or the instance's `defaultTemperature` | Not the provider's own default &mdash; VernLLM always sends a `temperature` unless told otherwise. Pass `null` to omit `temperature` from this call entirely, so the provider applies its own default.                                 |
| `maxTokens`       | `number`                                   | The instance's `defaultMaxTokens` (`1000`)    | Caps the length of the response.                                                                                                                                                                                                       |
| `reasoningEffort` | `'minimal' \| 'low' \| 'medium' \| 'high'` | Not sent                                      | OpenAI-style reasoning effort for reasoning models (o-series, gpt-5, etc.). Omitted from the request entirely if unset, so the provider's own default applies. Passed through as-is; providers/models that don't support it ignore it. |

## JSON & validation

<Cards>
  <Card title="jsonMode">
    `boolean`, default `true`, except default `false` when `tools` is set. When `true`, the
    response is parsed as JSON. Set to `false` to get the raw string content back untouched.
    Forced back to `true` if `jsonSchema` is set, even if you pass `jsonMode: false` explicitly.
  </Card>
  <Card title="jsonSchema">
    `JsonSchemaSpec`, optional. Provider-native JSON Schema structured-output mode
    (`{ name, schema, strict?, description? }`). Constrains generation itself rather than just
    validating after the fact. Implies `jsonMode: true`. See{' '}
    <a href="/docs/core/structured-output">Structured Output</a>.
  </Card>
  <Card title="schema">
    A Zod (or Zod-compatible, anything exposing `safeParse`) schema, optional. Validates the parsed
    JSON client-side. On failure, throws `LLMError('validation')` with `.issues` set to the
    validator's error object. If the provider response included usage data, that failure is
    reported to `onUsageFailure`, not `onUsage`. See <a href="/docs/core/usage-tracking">Usage
    Tracking</a>.
  </Card>
</Cards>

<Callout type="info">
  `schema` only runs if the call actually parses JSON. If you pass `jsonMode: false` without also
  setting `jsonSchema`, `call` throws `LLMError('validation')` before sending the request, rather
  than silently skipping validation and returning an unvalidated string cast to your schema's type.
</Callout>

## Request lifecycle

<Cards>
  <Card title="requestId">
    `string`, optional. Defaults to an auto-generated UUID. Passed through to `onUsage`,
    `onUsageFailure`, and relevant `onEvent` values so you can correlate an event or usage record
    back to the call that produced it. See{' '}
    <a href="/docs/core/usage-tracking">Token Usage Tracking</a>.
  </Card>
  <Card title="signal">
    `AbortSignal`, optional. If already aborted when `call()` is invoked, it throws
    `LLMError('aborted')` immediately without making a request. If it aborts mid-flight, the
    in-flight attempt and any pending retry delay are cancelled. For `cachedCall`, each caller has
    its own signal. Aborting one coalesced caller does not cancel the shared in-flight operation for
    other callers. See <a href="/docs/core/cancellation">Cancellation</a>.
  </Card>
</Cards>

## Usage metering

<Cards>
  <Card title="reserveUsage">
    Optional. Runs before any provider request is dispatched. Receives
    `{ coalesced, signal }`, where `coalesced` indicates whether the caller joined an existing
    cached in-flight operation and `signal` is the caller-supplied `AbortSignal` when provided.
    If it throws, the call stops and surfaces `LLMError('quota_exceeded')`. Retries do not call it
    again because it wraps the logical request, not individual attempts.
  </Card>
  <Card title="refundUsage">
    Optional. Runs when `reserveUsage` succeeded but the call ultimately fails. It receives the
    same `{ coalesced, signal }` shape. If a reservation succeeds and the request is aborted before
    the wrapped operation starts, the reservation is refunded. It is not called when
    `reserveUsage` itself fails because there was no reservation to refund.
  </Card>
</Cards>

<Callout>
  `reserveUsage` and `refundUsage` are application supplied hooks. VernLLM does not decide quota
  rules or billing policy; it only guarantees the reservation lifecycle around the request.
</Callout>

## Type parameter

`call<T>()` is generic over `T`, the shape of the parsed result:

- With `schema`, `T` is inferred from the schema (e.g. `z.infer<typeof MySchema>`) and the return
  value is a validated, typed `T`.
- Without `schema`, `T` defaults to `unknown` and you're responsible for narrowing the result
  yourself.

```ts title="generic-type-parameter.ts"
// result: { name: string; skills: string[] }
const result = await llm.call({
  userContent: resumeText,
  schema: CandidateSchema,
});

// result: unknown
const raw = await llm.call({ userContent: 'Hello' });
```
