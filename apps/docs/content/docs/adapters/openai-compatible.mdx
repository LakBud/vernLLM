Many hosted inference providers expose the same wire format as OpenAI's Chat Completions API. `VernLLM` includes a named adapter for each supported provider, but they're all thin aliases around the same OpenAI-compatible adapter: `fromOpenAICompatible()`.

<Callout title="Use fromOpenAI for OpenAI itself">
  For OpenAI, use the `fromOpenAI` alias rather than passing an `OpenAI` SDK instance straight to
  `client`. A raw client covers the basic non-streaming, text-only path structurally, but skips the
  multimodal `ContentBlock[]` translation and `createStream` wiring this adapter provides, and newer
  `openai` SDK majors have widened their content-part types in ways that no longer typecheck against
  `LLMClient` unwrapped. See [Migration Notes](/docs/migration-notes) for details.
</Callout>

The adapter preserves the OpenAI-compatible request shape and only normalizes fields VernLLM adds on top of the standard Chat Completions format. In particular, multimodal `ContentBlock[]` input is translated into OpenAI's native content array format, while plain string messages pass through unchanged.

The named adapters exist purely for readability and discoverability. They also leave room to introduce provider-specific behavior in the future without requiring a breaking API change.

## Named providers

<Callout title="These do not set baseURL for you">
  Mutating `client.baseURL` after construction does not work with the official OpenAI SDK. It
  reads `baseURL` once at construction time and never rereads a value assigned to it afterward. 
  Because of that, every named adapter below validates the client's `baseURL` instead of injecting one. 
  The check compares origins (protocol + host) only, not the full path, since a path like `/v1` 
  is an API-version or routing detail a provider can change independently of its identity. 
  If `baseURL` is missing or resolves to a different origin than the provider's known one, 
  the adapter throws an `LLMError` with `type: 'validation'` and 
  `issues: { expectedBaseURL, actualBaseURL }`, so callers using `isLLMError` can catch this the
  same way as vern-llm's other errors. Always set `baseURL` yourself, at construction time, when
  creating the client, using that provider's full documented path (the origin below plus its
  conventional path, e.g. `/v1`):
</Callout>

```ts title="correct-setup.ts"
import OpenAI from 'openai';
import { fromGroq } from 'vern-llm';

// Correct: baseURL passed at construction
const client = fromGroq(
  new OpenAI({
    apiKey: process.env.GROQ_API_KEY,
    baseURL: 'https://api.groq.com/openai/v1',
  }),
);
```

```ts title="incorrect-setup.ts"
import OpenAI from 'openai';
import { fromGroq, isLLMError } from 'vern-llm';

// Incorrect: this throws. The SDK ignores baseURL assigned after construction,
// so vern-llm cannot safely inject it for you.
try {
  const rawClient = new OpenAI({ apiKey: process.env.GROQ_API_KEY });
  const client = fromGroq(rawClient);
} catch (err) {
  if (isLLMError(err) && err.type === 'validation') {
    console.error(err.message);
    console.error(err.issues); // { expectedBaseURL, actualBaseURL }
  }
}
```

## Migrating from an older version

If you were already passing `baseURL` at construction time for every provider you use, nothing changes for you.

If you were relying on a named adapter to inject `baseURL` for you, that behavior never actually worked. An earlier version of this file tried to set `client.baseURL` after construction, but the official OpenAI SDK ignores that assignment, it only reads `baseURL` once, at construction time. So calls using an adapter like `fromGroq` without passing `baseURL` yourself were silently going to OpenAI's own endpoint using the provider's API key, which OpenAI rejects. Every named adapter now validates `baseURL` instead and throws immediately with the exact value to pass if it looks missing, so this failure mode is caught right away instead of producing a confusing 401.

Fix: pass `baseURL` directly inside the `new OpenAI({ ... })` call for every provider, using the value from the table above, not after the client is built.

Also note: the validation itself now only checks the origin (protocol + host), not the full path, so a path typo or an outdated `/v1` -> `/v2` style change on an otherwise-correct host will no longer throw. The corrected values below are still worth using since they're each provider's actual documented path, even though only the host portion is enforced.

A few endpoint values were also wrong or outdated and are now corrected:

| Adapter           | Old value                  | Correct value                             |
| ----------------- | -------------------------- | ----------------------------------------- |
| `fromNovita`      | `api.novita.ai/v3/openai`  | `api.novita.ai/openai`                    |
| `fromSiliconFlow` | `api.siliconflow.com/v1`   | `api.siliconflow.cn/v1`                   |
| `fromLambdaLabs`  | `api.lambdalabs.com/v1`    | `api.lambda.ai/v1`                        |
| `fromStepFun`     | `api.stepfun.com/v1`       | `api.stepfun.ai/v1`                       |
| `from01AI`        | `api.01.ai/v1`             | `api.lingyiwanwu.com/v1`                  |
| `fromNebius`      | `api.studio.nebius.com/v1` | `api.tokenfactory.nebius.com/v1`          |
| `fromTogether`    | `api.together.xyz/v1`      | `api.together.ai/v1` (`.xyz` still works) |

If you already had a `fromKlusterAI` client in code, kluster.ai is gone. Switch to another provider from the table above and update your API key.

If you already had a `fromGitHubModels` client in code, GitHub Models was fully retired on July 30, 2026 for every customer, including the playground, model catalog, inference API, and bring your own key. There is no replacement inside GitHub. Switch to another provider from the table above and update your API key.

If you use `fromAnyscale`, its self serve API was shut down in 2024. There is no fixed endpoint anymore, and this adapter throws if `baseURL` is missing. Pass `baseURL` for your own Anyscale Platform deployment.

Adapters with no fixed endpoint (Ollama, LM Studio, vLLM, Snowflake Cortex, Cloudflare Workers AI, Anyscale, Lepton) always required `baseURL` and still do. Nothing changes for these except that `fromBaseten`, `fromNvidiaNIM`, and `fromVercelAIGateway` were wrongly grouped with them in an earlier version of this file. Those three do have one fixed shared endpoint, listed in the table above, and now validate against it correctly instead of throwing unconditionally.

<Callout title="Adapters requiring baseURL">
  Some adapters have no fixed endpoint (self hosted like Ollama, LM Studio, vLLM, or
  account/deployment scoped like Snowflake Cortex, Cloudflare Workers AI, Anyscale). These throw an
  error immediately if the client has no `baseURL` set, rather than silently sending requests to
  OpenAI's own endpoint with the wrong key. Always set `baseURL` yourself when constructing the
  client for these.
</Callout>

<Callout title="Ollama Cloud">
  `fromOllama` has no default because most usage is a local server. Ollama also runs a hosted
  option, Ollama Cloud, with a fixed endpoint at `https://ollama.com/v1`. Pass that as `baseURL`
  yourself if you want the cloud option, it is never chosen automatically.
</Callout>

<Callout title="Lepton AI acquired by NVIDIA">
  Lepton AI was acquired by NVIDIA in 2025 and is now branded NVIDIA DGX Cloud Lepton. `fromLepton`
  has no confident default anymore, since the old per model endpoint pattern may no longer work. Set
  `baseURL` yourself and check current NVIDIA DGX Cloud Lepton docs for the right endpoint.
</Callout>

<Callout title="01.AI confidence">
  `from01AI`'s expected URL has only been confirmed via third party sources, not 01.AI's own docs
  directly. If a call fails, double check the current endpoint on 01.AI's site before assuming
  something else is wrong.
</Callout>

<Callout title="Regional accounts">
  A few providers split traffic by region with separate keys. StepFun's China accounts use
  `api.stepfun.com/v1` instead of the global default. MiniMax's China accounts use
  `api.minimaxi.com` instead of `api.minimax.io`. Pass `baseURL` explicitly for these.
</Callout>

<Callout title="kluster.ai removed">
  kluster.ai was acquired by MITO and its service was sunset in June 2026. `fromKlusterAI` has been
  removed. Migrate to another provider from the table above.
</Callout>

Don't see your provider? If it advertises itself as **OpenAI-compatible** or a **drop-in replacement for the OpenAI API**, it will typically work with `fromOpenAICompatible()` without any additional integration.

Adding a named adapter is just a convenience alias around the same implementation. If your provider isn't listed, feel free to open a PR, it's usually a one line addition.

```ts title="openai-compatible-setup.ts"
import OpenAI from 'openai';
import { VernLLM, fromOpenAICompatible } from 'vern-llm';

const llm = new VernLLM({
  client: fromOpenAICompatible(
    new OpenAI({
      apiKey: process.env.SOME_PROVIDER_API_KEY,
      baseURL: 'https://api.some-provider.example/v1',
    }),
  ),
  model: 'some-model',
});
```

## Tool calling

`tools`, `tool_choice`, and `tool_calls` already match the OpenAI Chat Completions shape, so this
adapter passes them through unchanged. The one normalization it applies is stripping
`is_error` from outgoing `tool` messages, since that field has no OpenAI-compatible equivalent
(`fromAnthropic` and `fromBedrock` honor it natively, mapping it to each provider's own
error-result field). See [Tool Calling](/docs/core/tool-calling) for the full
reference.

## Streaming

`fromOpenAICompatible` implements `createStream` by calling the same endpoint as `create` with
`stream: true`. No extra setup is needed beyond the client already passed to the adapter:

```ts title="openai-compatible-streaming.ts"
const { chunks, finalResult } = await llm.call({
  userContent: 'Write a short poem about the ocean.',
  stream: true,
});

for await (const chunk of chunks) {
  if (chunk.type === 'text-delta') process.stdout.write(chunk.delta);
}
```

<Callout>
  A final `usage` chunk requires the provider to support `stream_options: { include_usage: true }`.
  `fromOpenAICompatible` and its named aliases send this by default, `supportsStreamUsage` defaults
  to `true`. If your provider rejects unrecognized fields on a streaming request, pass{' '}
  `{ supportsStreamUsage: false }` as the second argument to omit `stream_options` entirely:
</Callout>

```ts title="openai-compatible-streaming-no-usage.ts"
const llm = new VernLLM({
  client: fromOpenAICompatible(client, { supportsStreamUsage: false }),
  model: 'some-model',
});
```

See [Streaming](/docs/core/streaming) for the full `stream: true` contract.

## Multimodal input

OpenAI-compatible providers with vision-capable models can receive images through VernLLM's
provider-independent `ContentBlock[]` format:

```ts title="openai-compatible-multimodal-input.ts"
const result = await llm.call({
  userContent: [
    {
      type: 'text',
      text: 'What is in this image?',
    },
    {
      type: 'image',
      mimeType: 'image/png',
      data: imageBase64,
    },
  ],
});
```

Image data must be raw base64-encoded bytes without a `data:` URL prefix. The OpenAI-compatible
adapter converts image blocks into the provider's expected `image_url` data URL format internally.

Supported image types are `image/png`, `image/jpeg`, `image/gif`, and `image/webp`.

Plain string `userContent` remains unchanged for text-only requests.
