Extensions add a capability inside VernLLM itself: logging, usage and budgets, routing, policy, and content checks.
Each is a separate package that depends only on `vern-llm`, so core stays small and you install
only what you use.

## What is an extension

An extension is a [middleware](/docs/core/middleware) that `vern-llm` provides capabilities for.
Core supplies what a middleware needs to work with others without knowing them: a place in the
nesting, per call state, custom events, and typed error codes for the rejections they share. The
contract is public, so a package from anyone else can follow it and be published through a
registry, and the packages listed here are the ones this repo ships.

## Extensions and integrations

|                        | Integrations                                                                             | Extensions                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Purpose                | Connect VernLLM to something outside your process (Redis, OpenTelemetry, a provider SDK) | Add a capability inside it (logging, usage, routing, policy, guard) |
| Third party dependency | Yes, as a peer or dependency                                                             | None                                                                |
| Folder                 | `packages/integrations/`                                                                 | `packages/extensions/`                                              |

See [Integrations](/docs/integrations) for the packages that reach outside your process.

## Shared rejection codes

An extension that denies a call does it with a typed `LLMError`, so callers and fallback policies
branch on one code whoever raised it. The core defines the codes. Extensions throw all but
`model_refused`, which the core throws when a provider declines a call:

| Code              | Type             | Raised by         | Meaning                                        |
| ----------------- | ---------------- | ----------------- | ---------------------------------------------- |
| `budget_exceeded` | `quota_exceeded` | `vern-llm-usage`  | A budget has no room for the call              |
| `policy_denied`   | `invalid_params` | `vern-llm-policy` | A policy removed every target or denied it     |
| `content_blocked` | `invalid_params` | `vern-llm-guard`  | A check refused the call or its answer         |
| `model_refused`   | `invalid_params` | `vern-llm`        | The provider declined the call, with no answer |

`budget_exceeded` and `policy_denied` reject a call before any provider is contacted.
`content_blocked` does too when a check refuses the call, but comes after the provider answered when
a check refuses the answer. `model_refused` always comes after the provider answered, so the refused
attempt can use tokens. None of them count toward the circuit breaker, and the logger records them
at `warn` as `rejected`. See
[Error Handling](/docs/core/error-handling) for the full list.

## What every extension follows

Extensions are plain [middleware](/docs/core/middleware), so each one is learned once and they
compose without knowing about each other. These rules hold for every package, and the logger is the
reference implementation.

| Rule                             | What it means                                                                                                                       |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| No imports between extensions    | Each package depends only on `vern-llm`. Anything one reads from another goes through `ctx.state`, custom events, or a shared shape |
| One instance per `VernLLM`       | A second one in the same `middleware` array throws at construction                                                                  |
| A fixed place in the nesting     | Order comes from a numeric `position`, so the order you list them in never matters                                                  |
| Namespaced, versioned events     | Custom events are named `<package>.<event>` and carry `v: 1` in their data                                                          |
| Own diagnostics through `logger` | A `logger` option for the package's own warnings, prefixed `[VernLLM] <package>:`                                                   |
| Never changes a call by accident | Only control extensions (usage, policy, guard, router) change an outcome, and only by a documented means                            |

Every call nests the same way, whichever order you build the extensions in:

```text title="extension-nesting.txt"
logger   position 'outermost'   sees everything, including denials
 └ guard  position -150         labels, redacts or blocks content
    └ policy position -100      removes forbidden targets
       └ usage position -50     budgets, priced at the most expensive allowed target
          └ router position 0   orders whatever is left
             └ attempts, retries, fallback
```

<Callout type="info">
  The logger is outermost, so its record includes calls that a guard, policy or a budget rejected. A
  rejection is logged at `warn` as `rejected`, not as an error.
</Callout>
