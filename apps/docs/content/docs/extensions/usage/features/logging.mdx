---
title: Logger and Events
description: Put cost on every vern-llm-logger record with usageLogFields, and react to budget warnings and rejections.
---

The two packages never import each other. They meet through `ctx.state` and custom events, and the
logger goes outermost so its record includes calls a budget rejected.

```ts title="logging-setup.ts"
import { loggerMiddleware } from 'vern-llm-logger';
import { usageLogFields, usageMiddleware } from 'vern-llm-usage';

const llm = new VernLLM({
  client,
  model: 'gpt-6-sol',
  middleware: [
    loggerMiddleware({ context: ['tenantId'], enrich: usageLogFields }),
    usageMiddleware({ prices, pricesAsOf, attribute: ['tenantId'], budgets, warnAt: 0.8 }),
  ],
});
```

## Cost in the record

`usageLogFields` lands in `record.fields`. For a stream it is set before the logger builds its
record at `finalResult`:

```json title="logging-record.json"
{
  "outcome": "ok",
  "fields": { "estimatedCostUsd": 0.0031, "wastedUsd": 0, "costSource": "table" },
  "custom": {
    "usage.budget_warning": [
      {
        "v": 1,
        "scope": "tenantId=acme per day",
        "unit": "usd",
        "limit": 50,
        "threshold": 0.8,
        "mode": "hard",
        "used": 0.81
      }
    ]
  }
}
```

A cache hit or join also carries `estimatedSavedUsd`, an estimate of the spend it spared.

`usageLogFields(ctx)` works on any middleware's `ctx` once the usage middleware's `next()` has
returned, and returns `{}` for a call that was not metered.

## How full a budget is

`usageBudgetShare(ctx)` returns the highest share of any budget the call falls under, counting
spend, holds in flight, and this call's own hold: `0.93` means 93% used. A soft budget can pass
`1`. It is set before `next()` runs, so any middleware inside usage, or your own `wrap`, can read it:

```ts title="logging-budget-share.ts"
import { usageBudgetShare } from 'vern-llm-usage';

const banner: VernLLMMiddleware = {
  name: 'banner',
  position: 0,
  wrap: async (request, next, ctx) => {
    const share = usageBudgetShare(ctx, { key: 'tenantId' });
    if (share !== undefined && share >= 0.9) notifyTenant(Math.round(share * 100));
    return next();
  },
};
```

| Option | Effect                                 |
| ------ | -------------------------------------- |
| `key`  | Only budgets on this context key       |
| `mode` | Only `'hard'` or only `'soft'` budgets |

The result is `undefined` when the call falls under no budget, or the store reported no figures: a
custom store without `used`, or a store error under `onStoreError: 'allow'`. The figures come back
with the reservation the call already makes, so there is no extra store round trip. The hold is
priced at the most expensive target the call may use, so near a hard limit the share can read
higher than the call you end up making. Acting well before the limit, or on a soft budget set
below a hard one, avoids that.

`usageLogFields` also carries `budgetShare`, the same highest share, so a record shows how close
each call was.

## Events

Both events are custom events with `v: 1`, kept by the logger's default `usage.*` allowlist.

| Event                   | When                                                                  | Data                                                           |
| ----------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------- |
| `usage.budget_warning`  | Once per threshold, budget and window, when spend plus holds reach it | `scope`, `unit`, `limit`, `threshold`, `mode`, `used` (0 to 1) |
| `usage.budget_exceeded` | A hard budget rejected a call, or a soft budget reached its limit     | `scope`, `unit`, `limit`, `remaining`, `mode`, `blocked`       |

A rejected call is logged at `warn` as `rejected`, with no attempts, not as an error.

<Callout type="info">
  With an asynchronous store, a stream's warning can reach the logger after its record is written,
  because the store read cannot finish in the same tick. Cost fields are never affected, and the in
  memory store is synchronous.
</Callout>
