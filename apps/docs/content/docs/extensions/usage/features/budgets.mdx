---
title: Budgets
description: Dollar and token limits per context value, checked before a call is sent with a reservation, and rejected with budget_exceeded.
---

A budget limits one `context` key over a calendar window. The key must also be listed in
`attribute`, so a budget always matches something that is attributed:

```ts title="budgets-config.ts"
usageMiddleware({
  prices,
  pricesAsOf: '2026-10-01',
  attribute: ['tenantId', 'feature'],
  budgets: [
    { key: 'tenantId', limitUsd: 50, per: 'day' },
    { key: 'feature', equals: 'summarize', limitTokens: 2_000_000, per: 'hour' },
  ],
});
```

Without `equals` the limit applies to every value of the key separately, so each tenant above gets
its own $50 a day. With `equals` it applies to that one value. A call without the key, or with no
`context`, is not limited by that budget. Set exactly one of `limitUsd` and `limitTokens`.

A budget is identified by its `key`, `equals`, unit and window, not by its place in the array or its
limit, so reordering the budgets or changing a limit keeps the spend a shared store already holds.
Two budgets with the same key, `equals`, unit, `per` and `mode` count the same spend twice, so they
throw at construction. A soft and a hard budget can share them, see below.

## Windows

Windows are calendar `hour`, `day` or `month`, in UTC unless you set `timeZone`. Spend starts again
from zero at the boundary. They follow the wall clock on purpose, since budgets are about the
calendar.

```ts title="time-zone.ts"
usageMiddleware({
  timeZone: 'America/New_York', // a day starts at New York midnight
  budgets: [{ key: 'tenantId', limitUsd: 50, per: 'day' }],
});
```

The zone applies to every budget and to `totals`. Daylight saving is followed, so a day can be 23 or
25 hours long. A repeated hour is two windows. An unknown zone throws at construction.

## How a call is checked

Before the call, an estimate is held against every budget it falls under. If any budget has no room,
nothing is held anywhere and the call is rejected.

<Steps>
<Step>

### Estimate

The worst case: the input plus `max_tokens`, priced at the dearest allowed target. The input counts
the messages, the tool definitions and the response schema.

</Step>
<Step>

### Reserve

The estimate is held against all budgets or none, in one atomic step.

</Step>
<Step>

### Call

Providers are contacted only now.

</Step>
<Step>

### Settle

The estimate is replaced by the real spend, or released when no usage was reported.

</Step>
</Steps>

The estimate counts `max_tokens` once and skips targets with no price, so with none priced only
tokens are held. Parallel calls are held against the budget before they run: 50 calls against a
budget with room for one let exactly one through.

A budget is checked before the cache, so a call that would have been a cache hit is rejected too
once the budget is spent, and while it runs it holds its worst case like any other call. A hit
itself spends nothing: its hold is freed.

The error message names the budget with the context value, such as `tenantId=acme per day`, so
show your users your own message instead of it.

A rejection is an `LLMError` with `type: 'quota_exceeded'` and `code: 'budget_exceeded'`. It is
thrown before any provider is contacted, never counts toward the circuit breaker, and the default
`fallbackOn` stops on it. A `usage.budget_exceeded` event says which budget was hit.

<Callout type="warn">
  Budgets are guards, not ledgers. Every call in flight can spend more than its estimate, since a
  longer answer or a larger input is only known at the end, so spend can pass a limit by the overrun
  of the calls that were running. Dollar budgets ignore unpriced calls, and token budgets count
  them.
</Callout>

## Soft budgets

A budget with `mode: 'soft'` alerts and never blocks, for visibility before enforcement. Pair it
with a hard budget on the same key for an alert before the block:

```ts title="soft-budget.ts"
usageMiddleware({
  prices,
  pricesAsOf: '2026-10-01',
  attribute: ['tenantId'],
  budgets: [
    { key: 'tenantId', limitUsd: 40, per: 'day', mode: 'soft' }, // alert at $40
    { key: 'tenantId', limitUsd: 50, per: 'day' }, // block at $50 ('hard' is the default)
  ],
});
```

A soft budget tracks spend and holds exactly like a hard one and never rejects a call. The first
time spend plus holds reach its limit in a window, `usage.budget_exceeded` is emitted once, with
`mode: 'soft'` and `blocked: false`. The call that crosses the limit completes, and the event comes
with it. A hard budget's rejection event carries `mode: 'hard'` and `blocked: true`.

`remaining()` keeps reporting a soft budget, with `mode`, `remaining` never below 0, and `overBy`
for how far past the limit it is. `warnAt` thresholds apply to soft budgets too, ahead of the alert.

A soft budget keeps its own counter, so the soft and hard budgets above each count the same calls
separately. Hard budgets are stored under the same keys as before, so existing spend carries on. A
custom store needs no change: a soft budget is handed to the store with a limit it can never reach.

## Alert thresholds

`warnAt` emits `usage.budget_warning` before a budget is hit. Give one share of the limit, or a list
for escalating alerts:

```ts title="warn-at.ts"
usageMiddleware({
  prices,
  pricesAsOf: '2026-10-01',
  attribute: ['tenantId'],
  budgets: [{ key: 'tenantId', limitUsd: 50, per: 'day' }],
  warnAt: [0.7, 0.9], // a single number such as 0.8 works too
});
```

Each value is strictly between 0 and 1. Every threshold is emitted once per budget and window, with
a `threshold` field saying which one. When a single call jumps past several at once, from 60% to
95% say, only the highest one is emitted and the lower ones count as done, so there is no burst of
stale alerts. A budget that has emitted its top threshold is not read again that window.

## When the store fails

`onStoreError: 'allow'` (the default) sends the call unmetered and logs the failure, matching the
core's rule that a failing cache is a miss. `'deny'` rejects it like an exceeded budget, with the
store's error as the `cause`, for teams where overspend is worse than downtime. The same goes for a
failure of the budget check itself, and for the default in memory store reaching its `maxScopes`,
which lets new scopes through when `onStoreError` is `'allow'` and rejects the call when it is
`'deny'`.

## Streams

A stream keeps its reservation until `finalResult` settles, then replaces it with the real spend.
A stream that is aborted reports no usage, but the provider still bills what it generated. Its
spend is unknown, so the hold stays as the spend: aborting a stream is not a way around a budget.
The call is counted under `unknownSpendCalls` in the totals, which add nothing to the cost for it.
A stream that fails some other way without reporting usage frees its hold.
