```ts title="guard-detector.ts"
type Detector = (
  segments: readonly Segment[],
  signal: AbortSignal,

```

- Pure: findings depend only on the segments. That is what makes the memo exact
- Batched: a detector gets every segment that needs scanning in one call
- Returning an array keeps the scan synchronous. A promise is awaited and raced against `timeoutMs`
- A threshold is one `.filter` inside your detector

<Callout type="warn">
  The built in detectors are heuristics. Run a new check in `mode: 'audit'` first.
</Callout>

`openaiModeration`, `llmClassifier` and `bedrockGuardrail` ask a provider instead of matching text. See
[Hosted detectors](/docs/extensions/guard/features/hosted-detectors).

### Reading more than text

A detector can say what else it takes with two optional properties.

```ts title="guard-capabilities.ts"
import type { Finding, ImageDetector, ImageSegment, Segment } from 'vern-llm-guard';

const hasImage = (segment: Segment | ImageSegment): segment is ImageSegment => 'image' in segment;

const unreadable: ImageDetector = Object.assign(
  (segments: readonly (Segment | ImageSegment)[]): Finding[] =>
    segments.flatMap((segment, index): Finding[] =>
      hasImage(segment) && segment.image.mimeType !== 'image/png'
        ? [{ segment: index, unscanned: true }]
        : [],
    ),
  { images: true as const },
);
```

- `images: true` gives the detector image segments as well as text. An image has no text, so a
  finding on one has no offsets. Return `{ segment, unscanned: true }` for an image you could not
  read, and it counts as unscanned instead of clean
- `callView: true` gives the detector a third argument, a `CallView` with the request's `input`
  segments and, once the answer exists, its `meta`. It is for output checks that depend on the call
- A `callView` detector is never memoized, since its findings depend on more than the text. It runs
  again for each attempt, so cache inside it if it is slow
- Image segments reach only detectors with `images: true`. Other detectors see the same segments as
  before

## When a detector fails

A detector that throws, times out or returns something invalid follows `onError`. With `closed`, a
blocking check blocks the call and a labeling check makes the labels unknown. With `open`, the
check is skipped. Results carry the check id and the kind of error, never its message.

## Parallel checks

```ts title="guard-parallel.ts"
{ id: 'jailbreak', detect: classifier, action: 'block', parallel: true }
```

- Starts with the call instead of before it, so a slow classifier adds no latency to calls that pass
- The answer is held until the check finishes. A streamed answer's first chunk waits for it
- On a block, a stream is cancelled and the call fails with `content_blocked`. A plain answer was
  already generated and billed: that is the cost of the latency win
- It runs after policy decided, so it can only block, and only on input. Anything else is a
  construction error
