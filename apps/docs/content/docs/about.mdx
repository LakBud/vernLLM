## Get LLM calls that survive scaling infrastructure

**VernLLM** is the LLM call framework: resilience, observability, and control for every call. It
runs inside your own process, so there is no gateway to deploy, no extra network hop, and no third
party that sees your prompts. The core package has zero runtime dependencies and stays under 120 KB.

```ts title="example.ts"
import Anthropic from '@anthropic-ai/sdk';
import OpenAI from 'openai';
import { VernLLM } from 'vern-llm';
import { fromAnthropic, fromOpenAI } from 'vern-llm/adapters';

const llm = new VernLLM({
  client: fromOpenAI(new OpenAI({ apiKey: process.env.OPENAI_API_KEY, maxRetries: 0 })),
  model: 'gpt-6-sol',

  // Resilience
  maxRetries: 3,
  timeoutMs: 10_000,
  circuitBreaker: true,
  retryBudget: { windowMs: 60_000, minCalls: 20, retryRatio: 0.2 },
  rateLimit: { requestsPerMinute: 500, maxConcurrent: 20 },
  fallback: {
    name: 'anthropic',
    client: fromAnthropic(new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY, maxRetries: 0 })),
    model: 'claude-opus-5-5',
    circuitBreaker: true,
  },

  // Observability
  onUsage: ({ totalTokens, context }) => {
    console.log(`${context?.tenantId} used ${totalTokens} tokens`);
  },
  onEvent: (event) => {
    if (event.kind === 'fallback') console.warn(`falling over from ${event.from} to ${event.to}`);
  },
});

const getWeather = {
  name: 'get_weather',
  description: 'Gets the current weather for a city',
  parameters: { type: 'object', properties: { city: { type: 'string' } }, required: ['city'] },
};

const city = 'Denver';

const { chunks, finalResult } = await llm.cachedCall({
  cacheKey: `weather:${city}`,
  ttl: 60,
  call: {
    userContent: `What's the weather in ${city}?`,
    tools: [getWeather],
    stream: true,
    // Control
    context: { tenantId: 't1' },
    deadlineMs: 20_000,
  },
});

for await (const chunk of chunks) {
  if (chunk.type === 'text-delta') process.stdout.write(chunk.delta);
}

const result = await finalResult; // cached, retried, fallen over if needed, and streamed
```

## The idea

Most LLM failures aren't exotic. A provider slows down, returns a 429, or answers 200 with something
unusable, and the app has to decide what to do next. A gateway can only make that decision from the
HTTP it sees. VernLLM makes it inside your process, where it knows what the call was for: the schema
the answer has to pass, the tenant it belongs to, and which providers it is allowed to use.

That is what the three pillars mean in practice:

- **Resilience:** a call keeps working when a provider fails, and a failing provider can't take your
  app down with it.
- **Observability:** every decision the call makes is reported, so nothing between your code and
  the provider is a black box.
- **Control:** your code, not a config file on another server, decides where a call goes and when it
  gives up.

## What happens to a call

<Steps>
<Step>

### Checked before anything is sent

Bad input, an unknown target, or a capability the model lacks throws a typed `invalid_params`
error right away. No provider is contacted, and no rate limit slot is used.

</Step>
<Step>

### Served from cache, or shared

With `cachedCall`, a hit returns at once. Concurrent misses for the same key share one provider
call, and a cache that errors is treated as a miss.

</Step>
<Step>

### Wrapped by your middleware

Each `wrap` middleware sees the whole call, outermost first. It can narrow which targets are
allowed, seed shared state, or answer without calling a provider at all.

</Step>
<Step>

### Tried target by target

`reserveUsage` checks your budget once for the whole call. Then each target checks its own circuit
breaker and rate limiter, and runs its own retry loop. Every
attempt is transformed, dispatched, parsed, validated, and checked for a soft failure. Retries back
off with jitter and stop when the retry budget or the deadline runs out.

</Step>
<Step>

### Fallen over, or stopped

When a target gives up, `fallbackOn` decides whether the next target could help or the call should
stop. A bad prompt stops. A sick provider moves on.

</Step>
<Step>

### Reported

Every retry, wait, circuit change, and fallback was reported as it happened. The result carries
which target answered, usage carries the call's `context`, and a failure carries every attempt.

</Step>
</Steps>

## Design principles

1. **Decide where the context is.** Reliability logic runs in your process, next to the code that
   knows what a good answer looks like.
2. **Blame the right party.** Caller mistakes, schema failures, and budget rejections never count
   against a provider's health.
3. **Isolate every target.** Each provider gets its own retries, breaker, limiter, and budget, and
   none are inherited.
4. **Never choose for you.** VernLLM runs the order you give it and never reorders on its own.
5. **Fail open where it's safe, closed where it isn't.** A broken cache only costs speed. A broken
   rate limiter stops calls instead of flooding a provider.
6. **Report, don't interfere.** Events are fire and forget, so a throwing handler can never change
   what a call does.
7. **Fail at construction, not in production.** Duplicate target names and invalid limits throw when
   the instance is built.
8. **Stay small.** Zero runtime dependencies, one bundle under 120 KB, and optional packages for
   everything else.

## What VernLLM isn't

It is not a gateway, so it has no proxy, dashboard, or key management. It is not an agent or UI
framework, and it never executes your tools. It counts tokens but ships no pricing table. For how
that compares with the tools that do, see [Why VernLLM](/docs/why).
