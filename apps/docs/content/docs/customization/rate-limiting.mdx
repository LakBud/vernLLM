<Callout type="info">
  The `RedisRateLimiter` example below is illustrative, showing the adapter shape.
  [vern-llm-redis](/docs/integrations/redis) is the production Redis backed limiter.
</Callout>

VernLLM ships `RateLimiter`, an in-process limiter built from `rateLimit`'s config object, plus a
`RateLimiterAdapter` interface for bringing your own (Redis, or anything else that coordinates across
processes):

```ts
interface RateLimiterAdapter {
  estimate(request: WireRequest): number;
  acquire(estimatedTokens: number, signal?: AbortSignal): Promise<RateLimitAcquireResult>;
  signalRateLimit(): void;
  reactToRateLimitHint(hint: ProviderRateLimitHint | undefined): void;
  getState?(): RateLimitState;
  readState?(): Promise<RateLimitState>;
  setLogger?(logger: Logger): void;
}
```

```ts title="redis-rate-limiter.ts"
import { VernLLM } from 'vern-llm';
import type { RateLimiterAdapter } from 'vern-llm';

class RedisRateLimiter implements RateLimiterAdapter {
  private cachedRemaining = 0;

  estimate(request) {
    return Math.ceil(JSON.stringify(request.messages).length / 4);
  }

  async acquire(estimatedTokens, signal) {
    await redis.acquire('llm:gpt-4o', estimatedTokens); // your own coordination
    this.cachedRemaining = await redis.remaining('llm:gpt-4o');
    return { release: () => redis.release('llm:gpt-4o', estimatedTokens), waitedMs: 0 };
  }

  signalRateLimit() {}
  reactToRateLimitHint() {}

  getState() {
    // getState is synchronous, so it reports the value cached on the last
    // acquire rather than making a fresh Redis round trip.
    return { requestsRemaining: this.cachedRemaining };
  }
}

const llm = new VernLLM({ client: openai, model: 'gpt-4o', rateLimit: new RedisRateLimiter() });
```

<Callout>
  `estimate`, `acquire`, `signalRateLimit`, and `reactToRateLimitHint` are required. The built-in
  `RateLimiter` already no-ops `signalRateLimit`/`reactToRateLimitHint` when `aimd` isn't
  configured, so a minimal custom limiter follows the same pattern rather than every call site
  needing an optional chain. `getState` is optional: leave it out if your limiter has no state worth
  reporting, and `llm.getRateLimitState()` simply returns `undefined`, same as it does for no
  limiter at all.
</Callout>

## Optional members

| Member      | Purpose                                                                                                                |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- |
| `getState`  | Synchronous levels for `llm.getRateLimitState()`. It can only report what the adapter already knows locally.           |
| `readState` | A live read for `llm.readRateLimitState()`. Without it, `readRateLimitState()` is answered from `getState`.            |
| `setLogger` | Receives the instance's `Logger`, so the adapter follows the same `logger` and `'silent'` settings as everything else. |

`readState` is for a limiter whose real levels live in a remote store: `getState` cannot wait for
that store, so the two answer different questions, "what do I know right now" and "what is the
truth". A failing `readState` rejects, since a live answer was asked for.

<Callout>
  `vern-llm` ships no distributed limiter itself, only this interface. Coordinating across processes
  is up to your implementation. For a limiter backed by a remote store, `VernLLM` helps with two
  optional members: `readState` for live levels through `llm.readRateLimitState()`, and `setLogger`
  so its background failures follow your logger, see [Optional members](#optional-members). See
  [Sharing a limiter across processes](/docs/core/rate-limiting#sharing-a-limiter-across-processes)
  in Core.
</Callout>
