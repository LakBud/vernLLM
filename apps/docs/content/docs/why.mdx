VernLLM is the LLM call framework: resilience, observability, and control for every call, running
inside your own process. Each one means something concrete:

- **Resilience.** Calls keep working when providers fail, and a failing provider can't take your app
  down with it.
- **Observability.** Every retry, fallback, wait, and breaker change is reported, tied to the call and
  the tenant that caused it.
- **Control.** Your code decides which providers a call may use, in what order, and when to give up.

The tools below overlap with it on retries and fallback, but each is built around a gateway that owns
keys, a model catalog, and billing. So each one is compared here as a client and gateway pair.

## Why in process

A gateway sees an HTTP request and an HTTP response. VernLLM sees the call: the schema the answer has
to pass, the tenant it belongs to, whether the caller already gave up, and which of your providers it
may use. That changes three things:

1. **It judges the answer, not the status code.** A 200 with an unusable body is a failure.
2. **It tells your fault from the provider's.** A bad request never opens the circuit for everyone.
3. **It adds nothing that can fail.** No extra network hop, no server to run, and prompts never pass
   through a third party.

## Resilience

### A 200 that isn't a success

Anthropic can send an `overloaded_error` inside a stream that already returned 200. Portkey's docs
note that by default [its gateway passes this to the client, so retry, fallback, and the circuit
breaker never run](https://portkey.ai/docs/aigw/integrations/llms/anthropic), since they key on status
codes. An opt in flag fixes it for Anthropic streams only.

VernLLM retries and falls back on any stream that fails before its first content chunk, even after a
keep-alive ping opened it. An empty body is a failure, JSON cut off at `max_tokens` becomes a
retryable `response_truncated`, and [`detectSoftFailure`](/docs/core/error-handling#soft-failure-detection)
turns anything else you consider broken, like a placeholder `N/A`, into a failure that retries,
falls back, and counts against that target's breaker.

### A primary that keeps failing

A common LiteLLM setup has one deployment and one fallback. A [LiteLLM
issue](https://github.com/BerriAI/litellm/issues/40405) shows that with the defaults, the primary is
never cooled down, so every request during an outage pays three failed attempts, 5 to 6 seconds,
before the fallback answers.

In VernLLM every target has its own [circuit breaker](/docs/core/circuit-breaker). Once the primary
opens, calls skip it without a provider attempt and go straight to the fallback. Recovery goes through
half open trial calls with a success ratio, not a timer, and a cooldown can grow on each repeat
open. Outcomes from calls admitted before the latest open are ignored, so a slow straggler can't close
the circuit. With [`vern-llm-redis`](/docs/integrations/redis) the state is shared and one process
wins each trial.

When every target is open, VernLLM fails fast with a `FallbackExhaustedError`. Portkey's documented
breaker [sends traffic to every target in that case](https://portkey.ai/docs/product/ai-gateway/circuit-breaker)
and closes once a fixed cooldown of at least 30 seconds passes, without a trial.

### A request that was never going to work

A client that can't stream, a forced tool choice a newer Claude model rejects, or a tool history with
a missing result all fail locally with a typed `invalid_params` error before any provider is
contacted. That saves a round trip, a rate limit slot, and a misleading provider error.

### One target starving another

Every target gets its own limiter, so a burst against a struggling primary can't use up the
concurrency a healthy fallback needs. With `isolateByModel`, one bad model can't open the circuit for
the others on the same provider.

### Your fault, not the provider's

A usage reservation is rejected, a caller sends a 4xx request, the model breaks a tool contract, or
the output fails your schema. None of these say the provider is unhealthy, so [none trip the
breaker](/docs/core/circuit-breaker#what-counts-as-a-failure). For parse, validation, quota, and
invalid input errors, `defaultFallbackOn` also stops instead of burning another provider on the same
bad input.

### An outage that turns into a retry storm

At 500 requests a second with 2 retries each, a provider failing half its calls pushes traffic toward
three times normal at the worst moment. A [retry budget](/docs/core/retry-budget) caps retries at a
share of each target's traffic. None of the others have one.

### Your provider's rate limit

With your own keys, the limit that matters is your account's requests and tokens per minute.
[Rate limiting](/docs/core/rate-limiting) estimates tokens before each call, queues within the limit,
reconciles with real usage, and shrinks the limit after a 429, or ahead of one when the provider
reports few requests left. `vern-llm-redis` shares the buckets, the queue, and the shrinking across
processes. LiteLLM's per deployment concurrency limit [has no wait
queue](https://docs.litellm.ai/docs/routing): a request over it gets a 429 at once.

### A cache that can't take you down

[`cachedCall`](/docs/core/caching) is built to stay out of the failure path. When many callers miss
the same key at once, one provider call serves all of them, streaming and plain calls alike, so a
cold cache can't stampede a struggling provider. A cache that errors is treated as a miss on read and
logged on write, so a Redis outage slows calls down instead of failing them. One caller aborting
never cancels the shared call for the others, and a hit never touches the provider or its breaker.

The cache also refuses to serve wrong answers: the in memory adapter copies values on write and read, a cached `null`
is a real hit, failed calls are never cached, and a missing or NaN `ttl` stores nothing instead of
an entry that never expires.

### A stream that stalls or is abandoned

Leaving a `for await` early cancels the provider stream and frees the rate limit slot. A slow reader
pauses the stream instead of losing chunks, `readerStallTimeoutMs` detaches one that stops reading,
and an idle chunk timeout catches a provider that stalls mid stream and counts it against the breaker.

```ts title="resilience.ts"
import { VernLLM } from 'vern-llm';
import { fromAnthropic, fromOpenAI } from 'vern-llm/adapters';

const llm = new VernLLM({
  client: fromAnthropic(anthropic),
  model: 'claude-opus-5-5',
  circuitBreaker: { threshold: 5, cooldownMs: 30_000, halfOpenProbes: 3 },
  retryBudget: { windowMs: 60_000, minCalls: 20, retryRatio: 0.2 },
  rateLimit: { requestsPerMinute: 500, tokensPerMinute: 100_000 },
  fallback: {
    name: 'openai',
    client: fromOpenAI(openai),
    model: 'gpt-6-sol',
    circuitBreaker: true,
  },
  detectSoftFailure: (result) =>
    typeof result === 'string' && result.trim() === 'N/A' ? 'soft_failure_detected' : undefined,
});
```

## Observability

A gateway log shows what the gateway did. VernLLM reports what happened to the call, including the
parts no gateway can see: a schema that failed, a soft failure, a local rate limit wait, or a
middleware that rewrote the request.

| Question                                | Where VernLLM answers it                                                                                                                                    |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Why did this call take 9 seconds?       | `rate_limited` with the wait, `retry` with the delay and whether `Retry-After` was honored, `fallback` with the time spent on each target                   |
| Was it us or the provider?              | OpenTelemetry attempt spans start when the request is sent, so queue time and transforms never inflate provider latency. Time to first chunk skips pings    |
| Which provider answered?                | `meta.current`, with `position` in the order tried, and `vernllm.answered.provider` on the span                                                             |
| Which tenant spent these tokens?        | The call's `context` rides on every event and every `TokenUsage`                                                                                            |
| Were we billed for a call that failed?  | A `usage_failure` event, `onUsageFailure`, and the `vernllm.usage_failure.count` metric                                                                     |
| How much came from the prompt cache?    | `cacheReadTokens` and `cacheWriteTokens` on usage, and the GenAI cache attributes on spans                                                                  |
| Is a breaker open right now?            | `getCircuitStates()`, `getFailureBreakdown()`, `getRetryBudgetState()`, `readRateLimitState()`, and the `vernllm.circuit.transitions` metric                |
| What did our routing middleware decide? | Middleware reports its own events with `ctx.emit`, and each becomes a span event                                                                            |
| Why was this call rejected?             | 12 error types and 38 codes. A breaker rejection says whether it is cooling down or waiting on a trial, and `getFailureBreakdown()` counts failures by code |
| What exactly was sent?                  | The `dispatch` hook sees each request after every transform. An `LLMError` keeps every attempt with a request snapshot, auth headers stripped               |

All of it flows through one [`onEvent`](/docs/core/observability) stream tagged with a `requestId`, and
[`vern-llm-otel`](/docs/integrations/otel) turns it into GenAI traces and metrics in your own
OpenTelemetry setup.

## Control

In a gateway, routing lives in a config header, a dashboard rule, or YAML on another server. In
VernLLM it is TypeScript in your repo: typed, reviewed, testable, and able to read anything your app
knows.

- **Per call target order.** `targets: ['bedrock', 'primary']` picks which providers one call may use
  and in what order. Nothing is created per call.
- **Policy that only narrows.** A `wrap` middleware can reorder or drop targets through
  `next({ targets })`. An inner one can never add back what an outer one removed, so a residency or
  compliance rule can't be undone further down.
- **Fallback decisions with context.** `fallbackOn` sees the error, the target that failed, and the
  one that would come next, and returns `'next'` or `'stop'`.
- **Call scoped data.** `context` carries a tenant or routing hint to every hook, event, and usage
  report. `state` seeds typed values for middleware before any hook runs.
- **Hands on the breaker.** `openCircuit()` drains a provider before maintenance, `closeCircuit()`
  brings it back, and a fallback target's breaker can be a shared adapter.
- **One clock.** `deadlineMs` bounds the whole call across retries and fallbacks, and
  `maxRetryAfterMs` caps how long a provider can make you wait.
- **No surprises.** VernLLM never reorders targets on its own, and bad config, such as duplicate
  target names or an invalid rate limit, throws at construction instead of in production.

```ts title="residency-policy.ts"
const residency: VernLLMMiddleware = {
  name: 'residency',
  wrap: (request, next, ctx) =>
    ctx.context?.region === 'eu'
      ? next({ targets: ctx.targets.filter((t) => t.name.startsWith('eu-')).map((t) => t.name) })
      : next(),
};

await llm.call({ userContent, context: { tenantId: 't1', region: 'eu' } });
```

## Built to be depended on

The core package has no runtime dependencies, so there is nothing transitive to audit, and CI caps
each published bundle at 120 KB. It ships with over 2,400 tests, CodeQL scanning, and coverage
gates, and every behavior change lands with a changeset that spells out what changes at runtime.

## Using them together

VernLLM has 38 OpenAI compatible adapters in `vern-llm/adapters`, including `fromVercelAIGateway`,
and a generic `fromOpenAICompatible`. LiteLLM Proxy and Portkey Gateway both speak the OpenAI format,
so a gateway can own keys, budgets, and the model catalog while VernLLM adds retry budgets, breakers,
and per target limits in your process.

Pick one retry owner, since each tool retries on its own. A gateway side fallback can also hide a
failing provider from VernLLM's breaker.

## Honest tradeoffs

1. VernLLM is an LLM call framework, not a gateway. No proxy, dashboard, key management, or limits on your
   own callers.
2. State is per process until you add [`vern-llm-redis`](/docs/integrations/redis).
3. No pricing table. Usage is token counts.
4. It is not an agent or UI framework, and it never executes tools for you.
5. Semantic caching is a [worked guide](/docs/guides/caching-methods/semantic), not a built in
   adapter.
6. It covers OpenAI compatible providers, Anthropic, and Gemini, Bedrock through
   [`vern-llm-bedrock`](/docs/integrations/bedrock), and `fromFetch` for the rest. The others list far
   more.
